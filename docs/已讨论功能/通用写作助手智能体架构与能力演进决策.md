## 一、三类执行体系的职责边界

### 1. 写作区单步任务执行器

- 服务于写作区内的单次功能型任务。
- 任务范围可为选区、本章或全文。
- 目标是单个明确任务的即时处理和直接响应。
- 可使用统一知识召回，但不需要通用 Agent 的长流程记忆和自主规划。

### 2. 知识沉淀 Workflow 执行器

- 服务于独立页面内按章节执行的预定义多步流程。
- 负责节点编排、状态推进、候选知识卡草稿生成和作者确认。
- 继续使用自身已有的运行记录、节点监控、人工审核和效果评测。
- 可使用统一知识召回，但不因此迁移到通用 Agent Runtime。

### 3. 通用写作助手 Agent Runtime

- 服务于任意规模的开放式小说写作相关请求，而不只是写作生成或复杂长任务。
- 请求可以小到询问主角曾做过的某件事、分析一句话是否符合人设，也可以大到规划、创作和审校多个章节。
- 高层编排 Agent 负责任务理解、高层规划、能力选择、动态执行、结果校验和必要的重规划；Runtime 为其提供循环、共享状态、调度、日志和恢复基础设施。
- 小请求应选择最小充分路径直接收敛；只有任务需要时才增加子 Agent、动态 DAG、运行时记忆、上下文压缩、人工中断和 checkpoint/resume。

## 二、共享基础能力，不共享业务运行模型

三类执行体系可以共享底层技术能力，包括统一知识召回、LLM 网关、存储契约和脱敏的技术遥测。

三者不统一以下业务设计：

- 业务运行日志。
- 任务状态机。
- 监控页面和人工介入模型。
- 成功标准和效果评测模型。

底层调用可以使用关联标识建立技术链路，但不得用通用调用轨迹替代某一执行体系的业务日志和评测记录。

## 三、Tool、Agent 与 Node 的已确认边界

### Tool

- Tool 是简单、单一职责、不包含 LLM 的可靠应用能力。
- Tool 必须具有结构化输入输出、稳定错误、超时和调用审计。
- 只有需要被 Agent 自主调用的应用能力才注册为 Tool，不把所有普通函数工具化。
- Tool 不得绕过应用层直接操作 MongoDB、Markdown 文件或其他基础设施。

### Agent

- Agent 是有明确目标、有 LLM 参与、能在授权范围内调用 Tool 的智能执行单元。
- Agent 必须输出结构化结果，并受模型、Token、Tool 调用次数、超时和重试上限约束。
- 简单子 Agent 可用普通异步 Handler 实现；复杂子 Agent 可在同一对外契约内封装独立 LangGraph 子图。
- 调用方不得同时依赖 Handler 和 Graph 两套协议，也不得取得原始 `CompiledStateGraph`。

### Node

- Node 是 LangGraph 的编排和状态边界，不等于 Agent。
- 顶层图未来可以包含 Agent 节点、确定性校验节点、人工中断节点和持久化节点。
- 普通 Tool 调用默认是所属 Agent 的子记录，不把每次读取、检索或计算都展开为主流程节点。

## 四、注册和权限边界

- 现有知识沉淀 Workflow 继续使用现有 Workflow/Agent 插件注册体系，本轮不重构。
- 通用子 Agent 使用独立 `SubagentManifest`、`SubagentRegistry` 和稳定的异步调用契约。
- Tool 使用独立 `ToolRegistry`，并按子 Agent 配置最小 Tool 权限。
- 三者可以复用少量值对象或 Protocol，但不得共用一个混合注册中心，也不通过共享父类耦合不同生命周期。

## 五、通用 Agent 的总体协作范式

通用写作助手整体采用“分层规划 + 子 Agent”的架构方向：

- 高层编排 Agent 维护全局目标、任务计划、关键上下文、依赖关系、执行节奏和质量收敛，不作为某个单点专家。
- Tool 和子 Agent 按稳定、可复用的能力边界设计，不按某个具体问题、页面流程或预设任务链设计。
- 子 Agent 提供边界清晰的专业判断、内容生产或质量校验能力；同一能力可以参与多种不同任务。
- 高层编排 Agent 根据当前请求决定直接回答、调用 Tool、调用单个子 Agent，还是组织顺序、并行、校验、修复和人工中断节点形成动态 DAG。
- 高层编排 Agent 在完整任务期间保持全局控制，不采用长链 Handoff 式的永久控制权转移。
- 不把纯 Router、长链 Handoff、经典 Manager-Worker 或 Blackboard 作为唯一主导范式；其中的路由、委派或共享产物机制可作为局部实现手段。

因此，Tool 和子 Agent 构成长期稳定的能力目录；计划、节点、边和 DAG 是针对单次请求生成的运行实例。不能先假定“检索—写作—检查—生成”等固定流程，再反向按流程节点定义能力。

第一版生产 Tool 与专业子 Agent 清单已经确认，见本文第十节。高层 Orchestrator Agent 仍属于阶段二 Runtime，不计入阶段一专业子 Agent 清单。

## 六、必须分开的两个实施阶段

### 阶段一：先完成真实 Tool 和真实子 Agent 能力层

本阶段必须将以下内容作为同一个完整能力实施：

- 真实可用的生产 Tool。
- 真实可用的生产子 Agent。
- Tool 和子 Agent 各自的 Schema、调用协议和注册契约。
- 任务上下文、业务范围、事实引用和中间产物的传递方式。
- Agent、LLM 和 Tool 的分层调用日志与关联方式。
- 每个子 Agent 的模型角色、Prompt、Tool 权限、结构化输出、校验方式和资源上限。

第一批能力的选择和验收应证明能力边界稳定、可独立调用且可被不同请求复用，不要求先拼成某条固定端到端任务链。真实 Tool 既可以由高层编排 Agent 直接调用，也可以由一个或多个子 Agent 在授权范围内调用。

不得为了验证 Runtime 而新增假 Tool、假 Agent（包括假子 Agent）或独立的测试型 `InvocationExecutor`。本阶段必须通过真实业务能力验证契约，不把“能调用一个假目标”当作交付结果。

### 阶段二：再基于真实能力搭建通用 Agent Runtime

只有阶段一的真实 Tool 和真实子 Agent 通过各自验收后，才进入 Runtime 实现。

Runtime 负责：

- 承载高层编排 Agent 对任意规模写作请求的理解、规划和执行循环。
- 根据请求选择直接回答、调用已注册 Tool、调用单个子 Agent 或构建多节点执行图。
- 组织顺序、并行、动态路由、有限修复循环和 DAG 依赖。
- 维护共享状态、人工中断、检查点、恢复和最终结果收敛。

Runtime 负责提供编排所需的状态、调度和执行机制，不负责某个专业领域的业务判断，也不负责在运行时临时补造未实现的 Tool 或子 Agent。高层编排 Agent 只能组合已注册的真实能力，不使用假能力完成验收。

阶段二后端、作者工作台、独立节点监控及专属效果评测已于 2026-07-14 落地：高层编排 Agent、顶层 LangGraph、动态 DAG 执行、有限校验与重规划、澄清和写入授权中断、独立检查点、恢复、取消、HTTP API、工作台交互、动态节点图、分层调用明细及五维确定性评测均已实现。评测不复用知识沉淀 Workflow 的字段匹配模型；创作类文风与叙事质量明确保留人工或后续语义裁判复核。

## 七、写操作和作者授权边界

- 写操作指持久化修改正文、章节、大纲、知识卡或设置；LLM 生成草稿和只读 Tool 调用不属于写操作。
- Agent 只能生成写入提案，不得直接持久化修改。
- 写 Tool 必须幂等，并且作者授权必须绑定 Tool、作用范围和规范化输入哈希；参数或内容变化后必须重新确认。
- 能力层先定义幂等和授权契约；暂停任务、展示差异、签发授权和恢复执行由阶段二的 Runtime 实现。

## 八、记忆能力的归属

- 运行时记忆是后续通用 Agent 和多步自主执行能力的基础设施。
- 其用于长流程管理、多轮上下文承接、关键信息复用和上下文压缩。
- 写作区单步任务和知识沉淀 Workflow 继续使用已有的上下文与运行记录，不为了统一而强制接入通用 Agent 记忆层。

## 九、已确认的能力演进顺序

1. 建立统一、可配置、可观测的知识召回能力。该基础已实现，当前为确定性词法召回、身份匹配和受限的有效知识目录读取。
2. 先完成真实 Tool、真实子 Agent，以及它们的 Schema、调用协议、上下文传递和分层日志。
3. 基于已验收的真实 Tool 与子 Agent 搭建通用 Agent Runtime，并引入异步编排和动态 DAG。该项后端已经实现。
4. 将向量 RAG 作为独立召回能力实现、评测和调优，只有在目标场景出现稳定收益后才通过统一召回层接入。
5. 建立通用 Agent 记忆层，支持结构化写入、检索、复用和上下文压缩，再接入 Runtime。
6. 在 Runtime、召回和记忆稳定后，推进通用 Agent 的业务节点流转监控、人工介入和产出评测。当前人工澄清、写入授权、作者工作台交互、独立节点监控及专属确定性评测已实现；创作类语义质量裁判仍属于后续增强项。
7. 基于真实业务记录和人工修正，沉淀高价值执行路径、失败模式、策略调优依据和长期运行经验。
8. 建立 checkpoint/resume，支持长链路任务在异常、超时、人工接管或系统重启后一致恢复，并将任务长度、成功率和恢复成功率纳入通用 Runtime 的治理体系。

以上顺序表示依赖关系和验收先后，不包含工时、人力或日期估算。

## 十、已确认的第一版能力目录

### 1. 十六个生产 Tool

小说正文与结构读取：

- `get_novel_structure`：读取卷章树、章节顺序、当前章节、标题、字数和状态。
- `read_manuscript`：按章节、章节范围或稳定来源引用读取 Markdown 正文。
- `search_manuscript`：在全文正文中搜索人物、事件、物品、对话和关键词证据。

已确认知识读取：

- `retrieve_knowledge`：根据问题和辅助上下文执行相关性召回。
- `resolve_knowledge_identity`：按知识类型、名称和别名解析具体实体。
- `list_knowledge_catalog`：按类型和分页条件浏览已确认知识目录。
- `read_knowledge_cards`：按稳定知识卡 ID 定向读取完整已确认知识。

外部资料研究：

- `search_external_sources`：根据明确研究问题搜索外部资料。
- `read_external_source`：读取指定外部来源并返回可引用内容。

外部资料 Tool 第一版真实实现，但默认禁止调用。只有用户明确要求联网、外部研究或核实外部资料时，Runtime 才能签发本次任务的外部访问许可；普通小说问题不得自动升级为联网任务。

正文与卷章结构写入：

- `preview_manuscript_patch`：校验正文补丁并生成差异预览，不执行持久化。
- `apply_manuscript_patch`：在作者授权后对章节正文执行真实持久化修改。
- `create_novel_structure_items`：在作者授权后创建卷或章节。
- `update_novel_structure`：在作者授权后重命名、调整顺序或修改卷章状态。
- `delete_novel_structure_items`：在作者二次确认后归档删除卷或章节。

已确认知识写入：

- `create_confirmed_knowledge`：消费作者确认后的确定输入，创建已确认知识卡。
- `update_confirmed_knowledge`：消费作者确认后的确定输入，更新已有已确认知识卡。

全部写 Tool 必须在第一版真实可运行，不允许只有 Manifest、空 Handler 或占位返回。专业子 Agent 只生成提案；只有高层编排 Agent 在取得与 Tool、资源范围和规范化输入哈希绑定的作者授权后，才能调用写 Tool。

### 2. 十二个专业子 Agent

- `canon_evidence`：小说内部事实问答、原文证据定位、事件链和不确定性说明。
- `external_research`：仅在用户明确授权外部研究时搜索、阅读和综合外部来源。
- `narrative_summary`：对章节、章节范围、人物经历或事件阶段进行结构化归纳。
- `worldbuilding`：世界规则、境界、功法、势力、地点和物品等设定设计与分析。
- `character`：人物动机、性格、能力、关系、成长和语言行为边界设计与分析。
- `story_architecture`：卷级、阶段级和跨章节的宏观剧情架构。
- `scene_planning`：章节、场景和叙事节拍的微观规划。
- `drafting`：新写、续写和扩写正文候选。
- `revision`：在保留原意和事实约束下改写、缩写、润色和调整正文。
- `consistency_reviewer`：统一检查设定、人物、时间线、因果和状态连续性。
- `narrative_reviewer`：检查节奏、冲突、信息释放、悬念、转折和读者理解成本。
- `style_reviewer`：检查措辞、句式、重复、叙述视角、人物口吻和文风一致性。

`consistency_reviewer` 对外保持一个 Agent 和一个调用契约，内部按设定、人物、时间线、因果、空间与状态连续性等维度维护独立检查定义和分维度评测，不拆成多个注册 Agent。

### 3. 已确认的拆分与非 Tool 决策

- `retrieve_knowledge`、`resolve_knowledge_identity`、`list_knowledge_catalog` 和 `read_knowledge_cards` 使用同一个统一召回层，但拥有独立 Tool Schema、调用语义、技术日志和评测指标。向量、图谱、混合检索和 Agentic RAG 是各能力内部可替换或组合的召回策略，不改变四个 Tool 的业务边界。
- `drafting` 与 `revision` 分开注册、路由模型和评测，分别优化新内容生成质量与修改后的原意保留质量。
- `story_architecture` 与 `scene_planning` 分开注册和评测，分别处理宏观结构与微观场景计划。
- `narrative_reviewer`、`style_reviewer` 和 `revision` 不合并：前两者发现不同类型的问题，后者消费修改目标并产出文本候选。
- 知识提案是子 Agent 输出和 Runtime 中间产物，不是 Tool。只有作者确认后的确定输入才能交给知识写 Tool。
- 字数、段落、句长、重复词、Diff、哈希和 Schema 校验等确定性处理属于应用服务、Agent 内部校验或 Runtime 基础设施，第一版不注册为独立 Tool。
- 用户问题、当前选区、当前章节、作者约束和运行预算由调用上下文传入，不创建读取这些固定输入的 Tool。
- 第一版不向通用 Agent 开放灵感、问题、章节摘要和待确认事实等创作工作区读取能力，后续另行讨论。
- 修改太初代码、数据库结构或前端按钮属于项目外部开发 Agent 或开发者职责，不属于通用写作助手 Tool。

## 十一、仍待技术验证的内容

- 每个 Tool 输入输出 Schema 的精确字段、预算默认值和错误码。
- 每个子 Agent 的完整 Prompt、默认模型映射、资源上限和质量阈值。
- 子 Agent 内部采用单次 Handler、有限修复循环还是内部 LangGraph 子图。
- 通用 Runtime 在真实模型上的计划稳定性、最大稳定节点数、并发上限和质量阈值。
- checkpoint/resume 在进程强制退出、外部调用不确定结果和长期运行场景下的恢复基准。
- 通用 Runtime 业务日志和中间产物的长期保留、归档与脱敏策略。
- 运行时记忆、上下文压缩和跨多轮任务复用策略。
- 通用 Runtime 的专属效果评测集、指标权重和模型基准。
