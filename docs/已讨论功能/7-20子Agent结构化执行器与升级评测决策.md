# 子 Agent 结构化执行器与升级评测决策

> 更新日期：2026-07-20
> 讨论日期：2026-07-20
> 状态：已确认待评测；当前默认形态保持为专业结构化执行器，后续按能力评测结果决定是否单独升级某个子 Agent

本文记录通用写作助手子 Agent 的能力形态与后续升级判断。本文不替代当前代码事实；实际输入 Schema、输出 Schema、工具权限、调用预算和 trace 字段仍以代码为准。

相关待办已写入系统问题与改进项记录：`issue-264b75f14ca842e199832f6d1c8b7217`。

## 一、已确认判断

当前通用写作助手的子 Agent 默认不是内部具备多轮思考、动态工具决策和行动循环的自主 Agent。

当前默认形态是专业结构化执行器：

```text
source_request 预取来源
→ 拼装专业任务输入
→ 一次模型执行
→ 结构化输出校验
→ 必要时只做 Schema 修复重试
→ 返回结构化结果
```

其中工具调用主要由代码根据 `source_request` 字段决定，例如读取正文、检索知识、读取知识卡、消费上游中间产物等；不是由子 Agent 在模型内部逐轮决定下一步要调用什么工具。

## 二、为什么默认保持结构化执行器

默认形态保持为专业结构化执行器，是为了让能力边界稳定、输入输出可校验、成本可控、调用记录可复现。

主编排 Agent 负责：

- 理解用户目标。
- 选择最小充分能力路径。
- 维护节点依赖。
- 管理运行状态、重规划和最终收敛。
- 判断各能力输出是否足以支撑最终回答。

子 Agent 负责：

- 在明确专业边界内处理材料。
- 消费必要正文、知识来源和上游中间产物。
- 输出结构化结论、来源引用、风险、不确定项和建议。

Tool 负责：

- 确定性读取、检索、写入预览、写入执行或校验。
- 保持结构化输入输出、权限边界和审计记录。

这种分层避免把所有工具结果、原文细节、知识细节和专业判断都塞进主编排 Agent。主编排 Agent 因此更专注于任务目标、路径选择、依赖管理和结果收敛，不被局部材料细节绑死。

## 三、上下文边界

主编排 Agent 与子 Agent 不共享同一套上下文拼装规则，这是已确认的合理边界。

主编排 Agent 的上下文服务于“如何拆任务和收敛结果”，包括当前请求、过程历史、运行记忆、计划摘要、节点摘要和能力目录。

子 Agent 的上下文服务于“如何完成一个专业任务”，包括专业任务输入、授权来源、上游中间产物和输出 Schema。

不能要求所有子 Agent 自动接收主编排 Agent 的完整上下文。这样会带来以下问题：

- 重复消耗大量上下文。
- 让子 Agent 接触与当前专业任务无关的计划细节。
- 增加输出漂移和职责混乱。
- 降低单个能力的可评测性。

子 Agent 需要知道的主链路信息，应由 Runtime 通过 `input_data`、`source_request.direct_context`、`source_request.upstream_artifact_refs` 或输入绑定显式传入。

## 四、什么时候升级某个子 Agent

默认不把所有子 Agent 升级为内部多轮自主 Agent。只有当评测或真实使用证明某个能力用单次结构化执行器效果不足时，才单独升级该能力。

可触发升级评估的现象包括：

- 一次检索经常无法取得关键来源，需要根据初次结果继续补查。
- 审校过程中发现问题后，需要反查角色设定、世界规则或前文状态。
- 写作任务需要先试写、再自审、再修订，而不是一次生成即可交付。
- 取证任务需要多轮消歧，才能确认人物、地点、事件或章节来源。
- 外部研究需要搜索、阅读、比较、补搜和补读。
- 子 Agent 输出经常带有未验证推断，或来源覆盖不足。

升级后的子 Agent 可以在内部封装 mini-runtime 或独立子图，但对外仍必须保持稳定能力契约。

## 五、升级时必须保持的契约

某个子 Agent 升级为内部多轮自主 Agent 时，主编排 Agent 不应感知其内部实现差异。

必须保持：

- `SubagentManifest` 中的能力名称和职责边界稳定。
- 输入 Schema 稳定，必要变更必须有兼容说明。
- 输出 Schema 稳定，仍返回结构化结果。
- 允许调用的 Tool 集合明确且最小化。
- 最大工具调用数、运行时间、输入上下文、输出 token 和重试次数有上限。
- 所有模型调用、工具调用和上游产物消费进入 trace。
- 失败、部分完成和不确定项必须显式返回或记录。
- 写入类动作仍由 Tool 授权机制控制，子 Agent 不直接绕过 Runtime 写入。

因此，主编排 Agent 始终只依赖能力契约：

```text
capability_name
input_data
structured output
source_refs
artifact_refs
trace_id
```

不依赖子 Agent 内部是“一次模型执行”还是“多轮工具决策”。

## 六、后续评测方向

后续对子 Agent 做能力评测时，应同时观察质量、成本和可复现性。

重点评测：

- 单次结构化执行是否能稳定取得足够来源。
- 输出是否包含清晰来源引用和不确定项。
- 是否存在因缺少二次取证导致的误判。
- 是否存在把运行记忆或摘要当成小说事实的风险。
- 上下文是否重复读取同一大块正文或知识。
- 结构化输出是否足以支撑主编排 Agent 最终收敛。
- 升级为内部多轮 Agent 后，质量提升是否足以抵消成本、复杂度和可控性损失。

评测结论应按能力分别记录，不做“一刀切”升级。

## 七、相关代码入口

- `src/taichu/application/subagents/runner.py`：当前子 Agent 的来源收集、模型调用和结构化校验入口。
- `src/taichu/application/subagents/models.py`：当前子 Agent 输入输出 Schema。
- `src/taichu/application/subagents/contract.py`：子 Agent Manifest、权限和资源限制契约。
- `src/taichu/application/general_agent/orchestrator.py`：主编排 Agent 的能力选择、计划物化和校验。
- `src/taichu/application/general_agent/executor.py`：DAG 节点执行、输入绑定、子 Agent 调用和上游产物传递。
- `src/taichu/application/general_agent/context.py`：主编排 Agent 的五层上下文组装与预算裁剪。
