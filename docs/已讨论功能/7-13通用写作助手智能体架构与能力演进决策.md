## 一、三类执行体系的职责边界

### 1. 写作区单步任务执行器

- 服务于写作区内的单次功能型任务。
- 任务范围可为选区、本章或全文。
- 目标是单个明确任务的即时处理和直接响应。
- 可使用统一知识召回，但不需要通用 Agent 的长流程记忆和自主规划。

### 2. 知识沉淀 Workflow 执行器

- 服务于独立页面内按章节执行的预定义多步流程。
- 负责节点编排、状态推进、候选知识卡草稿生成和作者确认。
- 继续使用自身已有的运行记录、节点监控、人工审核和效果评测。
- 可使用统一知识召回，但不因此迁移到通用 Agent Runtime。

### 3. 通用写作助手 Agent Runtime

- 服务于任意规模的开放式小说写作相关请求，而不只是写作生成或复杂长任务。
- 请求可以小到询问主角曾做过的某件事、分析一句话是否符合人设，也可以大到规划、创作和审校多个章节。
- 高层编排 Agent 负责任务理解、高层规划、能力选择、动态执行、结果校验和必要的重规划；Runtime 为其提供循环、共享状态、调度、日志和恢复基础设施。
- 小请求应选择最小充分路径直接收敛；只有任务需要时才增加子 Agent、动态 DAG、运行时记忆、上下文压缩、人工中断和 checkpoint/resume。

## 二、共享基础能力，不共享业务运行模型

三类执行体系可以共享底层技术能力，包括统一知识召回、LLM 网关、存储契约和脱敏的技术遥测。

三者不统一以下业务设计：

- 业务运行日志。
- 任务状态机。
- 监控页面和人工介入模型。
- 成功标准和效果评测模型。

底层调用可以使用关联标识建立技术链路，但不得用通用调用轨迹替代某一执行体系的业务日志和评测记录。

## 三、Tool、Agent 与 Node 的已确认边界

### Tool

- Tool 是简单、单一职责、不包含 LLM 的可靠应用能力。
- Tool 必须具有结构化输入输出、稳定错误、超时和调用审计。
- 只有需要被 Agent 自主调用的应用能力才注册为 Tool，不把所有普通函数工具化。
- Tool 不得绕过应用层直接操作 MongoDB、Markdown 文件或其他基础设施。

### Agent

- Agent 是有明确目标、有 LLM 参与、能在授权范围内调用 Tool 的智能执行单元。
- Agent 必须输出结构化结果，并受模型、Token、Tool 调用次数、超时和重试上限约束。
- 简单子 Agent 可用普通异步 Handler 实现；复杂子 Agent 可在同一对外契约内封装独立 LangGraph 子图。
- 调用方不得同时依赖 Handler 和 Graph 两套协议，也不得取得原始 `CompiledStateGraph`。

### Node

- Node 是 LangGraph 的编排和状态边界，不等于 Agent。
- 顶层图未来可以包含 Agent 节点、确定性校验节点、人工中断节点和持久化节点。
- 普通 Tool 调用默认是所属 Agent 的子记录，不把每次读取、检索或计算都展开为主流程节点。

## 四、注册和权限边界

- 现有知识沉淀 Workflow 继续使用现有 Workflow/Agent 插件注册体系，本轮不重构。
- 通用子 Agent 使用独立 `SubagentManifest`、`SubagentRegistry` 和稳定的异步调用契约。
- Tool 使用独立 `ToolRegistry`，并按子 Agent 配置最小 Tool 权限。
- 三者可以复用少量值对象或 Protocol，但不得共用一个混合注册中心，也不通过共享父类耦合不同生命周期。

## 五、通用 Agent 的总体协作范式

通用写作助手整体采用“分层规划 + 子 Agent”的架构方向：

- 高层编排 Agent 维护全局目标、任务计划、关键上下文、依赖关系、执行节奏和质量收敛，不作为某个单点专家。
- Tool 和子 Agent 按稳定、可复用的能力边界设计，不按某个具体问题、页面流程或预设任务链设计。
- 子 Agent 提供边界清晰的专业判断、内容生产或质量校验能力；同一能力可以参与多种不同任务。
- 高层编排 Agent 根据当前请求决定直接回答、调用 Tool、调用单个子 Agent，还是组织顺序、并行、校验、修复和人工中断节点形成动态 DAG。
- 高层编排 Agent 在完整任务期间保持全局控制，不采用长链 Handoff 式的永久控制权转移。
- 不把纯 Router、长链 Handoff、经典 Manager-Worker 或 Blackboard 作为唯一主导范式；其中的路由、委派或共享产物机制可作为局部实现手段。

因此，Tool 和子 Agent 构成长期稳定的能力目录；计划、节点、边和 DAG 是针对单次请求生成的运行实例。不能先假定“检索—写作—检查—生成”等固定流程，再反向按流程节点定义能力。

第一版生产 Tool 与专业子 Agent 清单已经确认，见本文第十节。高层 Orchestrator Agent 仍属于阶段二 Runtime，不计入阶段一专业子 Agent 清单。

## 六、必须分开的两个实施阶段

### 阶段一：先完成真实 Tool 和真实子 Agent 能力层

本阶段必须将以下内容作为同一个完整能力实施：

- 真实可用的生产 Tool。
- 真实可用的生产子 Agent。
- Tool 和子 Agent 各自的 Schema、调用协议和注册契约。
- 任务上下文、业务范围、事实引用和中间产物的传递方式。
- Agent、LLM 和 Tool 的分层调用日志与关联方式。
- 每个子 Agent 的模型角色、Prompt、Tool 权限、结构化输出、校验方式和资源上限。

第一批能力的选择和验收应证明能力边界稳定、可独立调用且可被不同请求复用，不要求先拼成某条固定端到端任务链。真实 Tool 既可以由高层编排 Agent 直接调用，也可以由一个或多个子 Agent 在授权范围内调用。

不得为了验证 Runtime 而新增假 Tool、假 Agent（包括假子 Agent）或独立的测试型 `InvocationExecutor`。本阶段必须通过真实业务能力验证契约，不把“能调用一个假目标”当作交付结果。

### 阶段二：再基于真实能力搭建通用 Agent Runtime

只有阶段一的真实 Tool 和真实子 Agent 通过各自验收后，才进入 Runtime 实现。

Runtime 负责：

- 承载高层编排 Agent 对任意规模写作请求的理解、规划和执行循环。
- 根据请求选择直接回答、调用已注册 Tool、调用单个子 Agent 或构建多节点执行图。
- 组织顺序、并行、动态路由、有限修复循环和 DAG 依赖。
- 维护共享状态、人工中断、检查点、恢复和最终结果收敛。

Runtime 负责提供编排所需的状态、调度和执行机制，不负责某个专业领域的业务判断，也不负责在运行时临时补造未实现的 Tool 或子 Agent。高层编排 Agent 只能组合已注册的真实能力，不使用假能力完成验收。

阶段二后端、作者工作台和独立节点监控已于 2026-07-14 落地：高层编排 Agent、顶层 LangGraph、动态 DAG 执行、有限校验与重规划、澄清和写入授权中断、独立检查点、恢复、取消、HTTP API、工作台交互、动态节点图及分层调用明细均已实现。旧五维确定性评测已经退出当前实现；当前评测入口统一为 `/api/general-agent-benchmarks`，以 `general_writing_agent_benchmark` Suite@2、严格选择、typed Oracle、六类硬门禁、逐案证据和不可变冻结目录为契约。Synthetic 37/37 已于 2026-07-31 冻结，真实模型轨道仍按独立运行身份闭环，创作类文风与叙事质量继续保留人工或语义裁判复核。

## 七、写操作和作者授权边界

- 写操作指持久化修改正文、章节、大纲、知识卡或设置；LLM 生成草稿和只读 Tool 调用不属于写操作。
- Agent 只能生成写入提案，不得直接持久化修改。
- 写 Tool 必须幂等，并且作者授权必须绑定 Tool、作用范围和规范化输入哈希；参数或内容变化后必须重新确认。
- 能力层先定义幂等和授权契约；暂停任务、展示差异、签发授权和恢复执行由阶段二的 Runtime 实现。

## 八、记忆能力的归属

- 运行时记忆是通用 Agent 和多步自主执行能力的基础设施，已于 2026-07-19 接入 Runtime。
- 其用于长流程管理、多轮上下文承接、关键信息复用和上下文压缩；不属于 MongoDB 知识卡，也不是小说事实兼容源。
- 运行记忆由 Runtime 自动写入、更新和过期，不经过作者确认，也没有草稿、确认、拒绝生命周期；作者硬约束、澄清修正、任务摘要、资源摘要、少量过程笔记和未解决项按不同保留策略进入工作记忆。
- 长章节、文件和节点输出不得整段写入运行记忆，只保存短摘要、来源引用和必要的产物引用。
- 事实类记忆只保存稳定来源引用和简短标签，消费时必须重新读取正文或统一召回，不允许把记忆摘要当成权威事实。
- 每次规划、重规划和校验使用五层冻结上下文快照：稳定背景、工作记忆、相关记忆、过程历史、当前请求。预算不足时依次收缩相关记忆、过程历史、工作记忆和稳定背景；当前请求必须完整保留。
- 恢复时优先复用同一快照；引用记忆已删除、过期或内容变化时重新组装并记录差异。外层运行图和计划内能力 DAG 都依赖 LangGraph 节点检查点恢复，不重跑已成功图节点；业务运行 JSON 只作为页面查询与审计投影，不参与决定续跑位置。
- 写作区单步任务和知识沉淀 Workflow 继续使用已有的上下文与运行记录，不为了统一而强制接入通用 Agent 记忆层。

## 九、已确认的能力演进顺序

1. 通过 `retrieve_story_context` 提供统一的正文与已确认知识卡 Graph RAG 证据入口，索引命中必须回读 Markdown 或 MongoDB 权威事实源后才能进入模型上下文。
2. 先完成真实 Tool、真实子 Agent，以及它们的 Schema、调用协议、上下文传递和分层日志。
3. 基于已验收的真实 Tool 与子 Agent 搭建通用 Agent Runtime，并引入异步编排和动态 DAG。该项后端已经实现。
4. 持续评测和调优 Graph RAG 的混合检索、图关系扩展、重排、权威回源和最终回答质量，并以自动化回归门禁约束生产链变更。
5. 建立通用 Agent 记忆层，支持结构化写入、检索、复用和上下文压缩，再接入 Runtime。该项已经实现：运行记忆与知识事实分库存放，`ContextAssembler` 在规划、重规划和校验前组装五层有预算上下文；记忆由 Runtime 全自动维护，作者工作台只读展示内容与来源，不提供手动新增或删除入口。
6. 在 Runtime、召回和记忆稳定后，推进通用 Agent 的业务节点流转监控、人工介入和产出评测。当前人工澄清、写入授权、作者工作台交互和独立节点监控已实现；固定评测基准、预检与硬门禁契约已建立，真实合成运行、语义裁判校准和可复验迭代闭环继续按规格推进。
7. 基于真实业务记录和人工修正，沉淀高价值执行路径、失败模式、策略调优依据和长期运行经验。
8. 建立 checkpoint/resume，支持长链路任务在异常、超时、人工接管或系统重启后一致恢复，并将任务长度、成功率和恢复成功率纳入通用 Runtime 的治理体系。

以上顺序表示依赖关系和验收先后，不包含工时、人力或日期估算。

### 向量召回追加决策（2026-07-18）

- 阶段 02 必须交付真实 Embedding、可重建向量索引、独立向量后端和与词法基线的同集评测，不采用随机或哈希向量冒充真实能力。
- 阶段 02 的质量结果不再产生“永久放弃向量召回”的分支；质量、成本或延迟不足时，应保留可复现数据并继续优化投影、模型、查询指令和向量候选规模。
- 阶段 02 不实现词法与向量融合，也不让向量结果替代生产词法结果。阶段 03 再单独讨论和实施混合召回、影子运行、融合策略及灰度顺序。
- 阶段 02 完成后，系统同时拥有可独立调用和评测的词法召回与向量召回能力；生产默认策略仍保持词法召回，是否以及如何融合由阶段 03 决定。
- 本条旧阶段决策已于 2026-08-15 被 `8-15Milvus向量图谱多跳召回决策.md` 取代：Qdrant 退出，保留本地 Qwen3-Embedding-4B，由 Milvus 同时保存正文片段、知识卡、实体与关系的可重建派生索引。
- 2026-07-19 阶段02独立向量能力完成三次60题重复评测，排名稳定且均为0个失败样例；但任务包要求语义改写 Recall@5 相比词法提升至少8个百分点，而词法基线已经是100%，因此融合结论必须为 `HOLD_HYBRID_QUALITY`。该结论只暂缓阶段03，不删除、降级或停用独立向量能力。

### 运行时记忆追加决策（2026-07-19）

- 运行时记忆、执行 checkpoint 和阶段 07 的长期运行经验是三类独立资产，不共享生命周期，也不互相充当事实源。
- 运行记忆使用派生 JSON 记录和可重建词法索引，不写入 MongoDB 知识卡集合，不复用知识向量索引。
- 一个侧栏对话窗口唯一对应一个 `conversation_id（会话标识）`，窗口内每次用户请求递增 `request_index（请求序号）`；只有用户点击“新对话”才创建新会话。旧运行缺少会话标识时优先按共同 `task_id（任务标识）` 归并，不能按每次 `run_id（运行标识）` 拆分。
- 删除单次运行不级联删除会话记忆；删除整个会话时自动软删除该会话全部运行记忆。
- 自动运行记忆没有作者确认生命周期。短期资源摘要和过程笔记按请求序号自动退出当前上下文，用户指令和任务摘要按策略保留。
- 运行记忆属于 Agent 内部运行状态，不是作者直接编辑的业务数据。作者只能通过正常对话或 Human-in-the-loop（人工介入）节点影响 Agent，不能手动新增、修改或删除单条运行记忆；工作台和公开 API 对单条运行记忆只提供只读观察能力。
- 记忆纠错、冲突处理、替代、过期和清理由 Runtime 策略负责。删除整个会话时允许系统级联清理该会话的运行记忆，这属于会话生命周期管理，不属于用户直接操纵记忆。
- 此边界是 Agent 交互安全约束：前端、公开 API、Tool、子 Agent 和 Prompt 都不得重新引入单条运行记忆的增删改入口。作者提出修正时，Runtime 应从对话或人工介入结果生成新的运行状态，并按策略处理旧记忆，不要求作者理解或维护底层记忆结构。
- 页面中的“第 N 次请求自动记录”只说明 Runtime 在哪次请求中产生了该条运行状态，不表示作者能够手工保存；页面不得为该条目配置新增、编辑或删除操作。
- 第一版上下文压缩使用确定性结构化压缩，不新增模型调用；压缩失败时必须返回保留当前请求和用户指令的非空安全摘要。
- 能力目录采用两阶段渐进式披露。第一阶段始终向编排 Agent 提供全部已注册 Tool 与子 Agent 的轻量索引，包括能力名称、类型、中文职责、权限属性，以及子 Agent 可调用 Tool 等规划必需信息；不得再按相关性、固定数量或注册顺序静默裁掉能力。
- 第一阶段只选择能力和依赖骨架，不生成调用参数。第二阶段只加载本次已选能力的完整输入输出 Schema，由模型补齐参数和产物绑定；第二阶段不得改变第一阶段确定的能力、节点或依赖关系。
- 轻量目录和已选能力完整契约分别使用独立硬预算。任一内容超过预算时必须显式失败并说明原因，不得通过遗漏已注册能力规避预算。
- 对“第八章讲了什么”这类章节顺序已知的正文问题，规划器必须优先调用 `read_manuscript（读取正文）` 定向读取对应章节，再按需要交给归纳能力；不得用全文模糊搜索替代定向读取。若最终成功节点没有 `manuscript:（正文来源）` 引用，质量门禁必须触发有限重规划，仍未取得正文来源时以失败收敛，禁止推测正文不存在。

### 上下文审计与模型回放追加决策（2026-07-21）

- 五层上下文是编排模型某个阶段的受预算输入，不等于完整会话历史、子 Agent 输入、模型调用回放或 LangGraph 检查点。
- 每次规划、每次重规划和校验组装完成后都必须追加保存独立上下文快照。业务运行投影和图状态只保留最新快照用于页面摘要与恢复判断，完整阶段历史独立存放，避免检查点随历史线性放大。
- 一个侧栏对话的完整业务交流可由各次运行的 `messages（消息）`、`user_goal（用户目标）`、人工请求和 `final_answer（最终回答）` 还原；五层上下文只选择其中当前模型需要的受预算部分，不承担永久对话原文仓储职责。
- 生产统一 LLM 网关必须为带 `run_id（运行标识）` 的主编排和专业子 Agent 调用保存脱敏后的实际角色消息与规范化响应，用于质量评测和问题回放；技术调用追踪继续只保存哈希、计量与状态，不能替代调用原文。
- 模型回放不得保存 HTTP 鉴权头、API Key 或供应商原始响应包；常见密钥片段必须在落盘前脱敏。删除单次运行时同步清理该运行的上下文快照历史和模型调用回放。
- 前端上下文入口默认查看当前会话最新请求，并允许选择历史请求和该请求内的规划、重规划、校验阶段。模型调用回放当前只提供后端只读接口，后续评测页面按需消费，不与作者可编辑记忆混合展示。
- LangGraph 检查点仍是执行位置与恢复状态的权威来源；业务运行 JSON、五层上下文历史、模型回放和运行记忆都不能替代图检查点决定从哪个节点续跑。

### 后续阶段调整决策（2026-07-20）

- 阶段 05 自适应模型路由暂缓，生产继续使用现有静态 `ModelRoleRouter（模型角色路由器）` 与显式角色配置；暂缓不表示删除后续扩展入口。
- 下一目标直接进入阶段 06“检查点恢复可靠性与长链路基准”。阶段 06 不得等待尚未实现的自适应路由能力，也不得把自适应路由快照作为本阶段启动前提。
- 作者期望阶段 06 利用 LangGraph 自身的检查点与恢复机制。正式技术设计前必须先向作者确认恢复职责边界；确认前不形成定稿设计、不实施恢复代码。

### 阶段 06 实施结论（2026-07-20）

- 阶段 06 当前结论为 `PASS_WITH_LIMITS（有限通过）`。能力 DAG 已改为真实 LangGraph 动态图；同一 `run_id（运行标识）` 作为线程标识，每个计划修订使用独立检查点命名空间，服务重启和失败恢复继续同一次运行，不另建一次用户请求。
- 检查点仓储已使用原子替换、哈希链修订、最新有效指针、损坏回退和旧平面文件迁移；业务运行 JSON 不再承担执行恢复职责。
- 六个生产写 Tool 已全部注册真实资源对账器和追加式副作用记录。真实写入后、节点检查点前发生中断时先对账；确认已写入则复用结果，确认未写入才在原授权范围内继续，无法确认则停止并要求人工处理。
- 本地确定性恢复基准共 36 组，覆盖 1/3/6/12/20/40 个节点、并发 1/3/8、正常执行和进程中断；完成率 100%、恢复成功率 100%、重复成功执行 0。最大检查点占用约 7.63 MiB。
- 本地基准证明 40 节点、并发 8 可执行，但不能替代真实模型生产基准。真实模型三次重复、重规划 0/1/3 次、模型超时、召回回退和读写混合长任务尚未执行，因此产品默认继续保持 12 节点、并发 3、最长 900 秒、每次授权最多一个写节点；提高上限必须由后续付费基准支持。

## 十、已确认的第一版能力目录

### 1. 十六个生产 Tool

小说正文与结构读取：

- `get_novel_structure`：读取卷章树、章节顺序、当前章节、标题、字数和状态。
- `read_manuscript`：按章节、章节范围或稳定来源引用读取 Markdown 正文。
- `retrieve_story_context`：对未知位置的正文和知识卡统一执行 Milvus BM25、稠密向量、Vector Graph 多跳、RRF 与 BGE 重排，返回完成事实源回读的证据。

已确认知识读取：

- `resolve_knowledge_identity`：按知识类型、名称和别名解析具体实体。
- `list_knowledge_catalog`：按类型和分页条件浏览已确认知识目录。
- `read_knowledge_cards`：按稳定知识卡 ID 定向读取完整已确认知识。

外部资料研究：

- `search_external_sources`：根据明确研究问题搜索外部资料。
- `read_external_source`：读取指定外部来源并返回可引用内容。

外部资料 Tool 第一版真实实现，但默认禁止调用。只有用户明确要求联网、外部研究或核实外部资料时，Runtime 才能签发本次任务的外部访问许可；普通小说问题不得自动升级为联网任务。

正文与卷章结构写入：

- `preview_manuscript_patch`：校验正文补丁并生成差异预览，不执行持久化。
- `apply_manuscript_patch`：在作者授权后对章节正文执行真实持久化修改。
- `create_novel_structure_items`：在作者授权后创建卷或章节。
- `update_novel_structure`：在作者授权后重命名、调整顺序或修改卷章状态。
- `delete_novel_structure_items`：在作者二次确认后归档删除卷或章节。

已确认知识写入：

- `create_confirmed_knowledge`：消费作者确认后的确定输入，创建已确认知识卡。
- `update_confirmed_knowledge`：消费作者确认后的确定输入，更新已有已确认知识卡。

全部写 Tool 必须在第一版真实可运行，不允许只有 Manifest、空 Handler 或占位返回。专业子 Agent 只生成提案；只有高层编排 Agent 在取得与 Tool、资源范围和规范化输入哈希绑定的作者授权后，才能调用写 Tool。

### 2. 十二个专业子 Agent

- `canon_evidence`：小说内部事实问答、原文证据定位、事件链和不确定性说明。
- `external_research`：仅在用户明确授权外部研究时搜索、阅读和综合外部来源。
- `narrative_summary`：对章节、章节范围、人物经历或事件阶段进行结构化归纳。
- `worldbuilding`：世界规则、境界、功法、势力、地点和物品等设定设计与分析。
- `character`：人物动机、性格、能力、关系、成长和语言行为边界设计与分析。
- `story_architecture`：卷级、阶段级和跨章节的宏观剧情架构。
- `scene_planning`：章节、场景和叙事节拍的微观规划。
- `drafting`：新写、续写和扩写正文候选。
- `revision`：在保留原意和事实约束下改写、缩写、润色和调整正文。
- `consistency_reviewer`：统一检查设定、人物、时间线、因果和状态连续性。
- `narrative_reviewer`：检查节奏、冲突、信息释放、悬念、转折和读者理解成本。
- `style_reviewer`：检查措辞、句式、重复、叙述视角、人物口吻和文风一致性。

`consistency_reviewer` 对外保持一个 Agent 和一个调用契约，内部按设定、人物、时间线、因果、空间与状态连续性等维度维护独立检查定义和分维度评测，不拆成多个注册 Agent。

### 3. 已确认的拆分与非 Tool 决策

- `retrieve_story_context` 负责相关性检索；`resolve_knowledge_identity` 和 `list_knowledge_catalog` 直接查询 MongoDB；`read_knowledge_cards` 按稳定 ID 读取完整权威对象。四者拥有独立 Tool Schema、调用语义、技术日志和评测指标，不能以一个通用搜索接口模糊职责。
- `drafting` 与 `revision` 分开注册、路由模型和评测，分别优化新内容生成质量与修改后的原意保留质量。
- `story_architecture` 与 `scene_planning` 分开注册和评测，分别处理宏观结构与微观场景计划。
- `narrative_reviewer`、`style_reviewer` 和 `revision` 不合并：前两者发现不同类型的问题，后者消费修改目标并产出文本候选。
- 知识提案是子 Agent 输出和 Runtime 中间产物，不是 Tool。只有作者确认后的确定输入才能交给知识写 Tool。
- 字数、段落、句长、重复词、Diff、哈希和 Schema 校验等确定性处理属于应用服务、Agent 内部校验或 Runtime 基础设施，第一版不注册为独立 Tool。
- 用户问题、当前选区、当前章节、作者约束和运行预算由调用上下文传入，不创建读取这些固定输入的 Tool。
- 第一版不向通用 Agent 开放灵感、问题、章节摘要和待确认事实等创作工作区读取能力，后续另行讨论。
- 修改太初代码、数据库结构或前端按钮属于项目外部开发 Agent 或开发者职责，不属于通用写作助手 Tool。

## 十一、通用 Agent 评测追加决策（2026-07-29）

- 当前固定评测只服务太初研发人员，目标是证明通用 Agent 主链路能够真实运行，并检验后端 Runtime、能力调用、上下文治理、人工中断与恢复等架构边界是否合理。
- 直接产出是通用 Agent 评测页的可审计运行结果。后续接入新模型时，可以用同一固定基线检查合同完成情况、接入可用性和必要的资源数据，但当前不形成模型排行榜。
- 当前评测不接线上真实流量，不承担长期动态模型效果监控，也不试图用一次运行说明模型的长期稳定性。执行顺序固定为：先用不变的合成基线验证 Harness，再用固定套件运行真实模型。
- 成功不等于把更多模型标成“通过”。评测发现 Runtime、评测 Harness、上下文组装、模型网关或证据链缺陷时，必须先修复系统问题并复验，不能放宽合同或为了得到好看结果改写门禁。
- 页面只展示研发定位需要的套件范围、合同完成情况、模型调用是否真正发生、接入阻断、必要 Token、耗时、费用和工件身份；不显示名次，不把能力、可用性、成本和时延合成单一总分。
- `passed（通过）`只表示该次运行满足固定合同和六类硬门禁；`failed（未通过）`表示真实运行已经发生但合同未闭合；`blocked（接入阻断）`表示请求未成功进入模型推理。三者用于定位链路，不作为模型能力排名。
- 37 条固定合同不宣称覆盖全部小说写作请求。当前优先覆盖最小充分路由、检索与证据、多 Agent 数据交接、预览/授权/拒绝/持久化、运行记忆、八种恢复故障注入和八种上下文压力等最能暴露 Agent 架构错误的能力边界；任务不设置权重。
- 预算、验证器、产物、停止原因、授权安全和证据六类硬门禁对首轮合同履约判定已经足够。输出质量、一致性、引用真实性和长周期状态一致性暂不新增为硬门禁，避免在第一阶段把主观判断混入确定性合同。
- 第 30—37 条已经覆盖长历史、长工作记忆、大节点输出、多来源共同超限、压缩前后结果合同等价、无效记忆隔离、至少 12,000 字符的原始当前请求，以及无法安全容纳时在能力调用前拒绝。它们验证确定性 Synthetic 行为合同；长上下文续写、长周期偏好记忆一致性和真实模型在压力下的质量稳定性仍属于后续独立专项，不能用 Synthetic 37/37 代替。
- 代码、套件、夹具、能力目录、案例集合、逐案预算、授权策略、解码策略、运行环境摘要、模型运行、比较工件和索引身份继续冻结；环境变量、Provider 映射、网关版本、依赖版本和运行机器资源状态当前不要求完全冻结，但发生接入异常时必须保留足以区分本地环境、网关拒绝和模型输出的审计证据。
