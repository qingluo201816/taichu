总体原则
通用字段只保留所有知识卡都真正需要的内容。不要把人物、地点、事件的专属字段塞进通用层。
类型字段要围绕写作时的检索问题设计。例如人物卡要回答“这个人现在是谁、在哪里、什么境界、和谁有关系”，事件卡要回答“发生了什么、造成什么变化”。
伏笔卡暂时不太需要，把相关设计先删除了不要做兼容或保留，后面系统稳定了再来设计
稳定事实和阶段状态应分开。角色境界、所在地、阵营、持有物会随章节变化，不适合作为单个可覆盖字段长期保存，应进入按章节或时间点记录的状态表。
来源引用应成为有效知识卡的基础约束。草稿可以没有来源；标记有效时至少要有indox事实转化，agent正文自动提取，人工添加，其中的一个来源。inbox事实转化 = 来自收件箱中待处理事实，经过确认后转成知识卡 agent正文自动提取 = 从正文、章节文本中由 AI 自动抽取出的知识（还未实现，保留字段） 人工添加 = 作者手动创建或手动补充的知识
字段类型应尽量结构化：枚举、数字、布尔、章节引用、知识卡引用、短文本、长文本分清楚。后续检索、排序、冲突检测和 AI 引用都依赖这个边界。

架构设计建议
建立后端字段 schema 注册表
建议后端维护每种知识卡的 schema，而不是把字段结构写死在前端表单里。schema 至少包含：

配置项	说明
field_key	字段键名
label	中文展示名
field_type	文本、长文本、枚举、数字、布尔、章节引用、知识卡引用、数组、记录数组
required_when_active	标记有效时是否必填
options	枚举选项
placeholder	输入提示
display_group	编辑界面分组
list_display	是否在收缩条目中展示
ai_usage	供 AI 检索时的用途提示
前端通过 schema 渲染编辑表单，可以避免每增加一种卡片就改大量 UI 代码。

引用统一使用 ID，不使用名称字符串
人物、地点、势力、物品之间的关联字段应尽量保存知识卡 id，前端展示时再解析成名称。名称可以修改，ID 不应变化。这样能支持：

重命名后不丢关系。
删除或废弃卡片时能提示影响范围。
AI 检索时能沿关系图扩展上下文。
后续做重复卡片合并时更安全。
前端编辑形态建议
编辑界面不建议回到大表格。更适合的结构是：

收缩列表只展示名称、摘要、状态、重要程度和少量关键字段。
点击条目后进入详情或侧边面板。
详情页按“基础信息”“类型字段”“状态记录”“关系”“来源”分段。
次级操作放在条目右侧展开菜单中。
字段为空时不要展示大面积空框，只显示“添加字段”或轻量占位。
这与当前知识库布局优化方向一致，也方便后续字段数量增加时保持界面干净。
