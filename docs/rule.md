# 项目资料规则

## 文件命名

- `docs/学习资料/`、`docs/已讨论功能/`、`docs/旧历史/` 下的普通文章及配套文件保留日期前缀，并以中文主题命名。
- 普通文章统一使用 `月-日中文主题.扩展名`；日期取首次形成、首次讨论或归档日期，后续修订不反复改名。
- 各资料目录的长期说明是唯一例外，统一命名为 `说明.md`，不添加日期前缀，也不在正文维护更新日期。
- 文件名应直接表达主题；同一文章的 Mermaid、PNG、SVG 等配套文件使用相同日期前缀和主题名。
- 具有独立追溯意义的备份目录可以保留完整日期前缀。
- 任务包、明确按批次保存的执行工件和其他专用目录，按各自规则命名。

## 资料分类

- `docs/学习资料/` 保存对太初具体实现主题的教学式讲解。凡涉及当前行为，生成前必须核对当前源码、测试、配置与运行结果；尚未落地的目标实现必须明确标出事实与设想边界。具体风格和参考样本见 `docs/学习资料/说明.md`。
- `docs/已讨论功能/` 保存用户在多轮讨论中与 Codex 共同建设的未来计划。计划不是当前代码事实，实现后必须补充真实入口和验证结果。
- `docs/旧历史/` 只保存已经废弃、已经被替代或明确不再采用的旧方案与旧实现快照。目录中的内容不得参与当前实现决策。
- `docs/前端风格/` 保存前端视觉资料；当前强制设计规则仍以根目录 `DESIGN.md` 为准。
- `docs/任务包/` 保存可执行任务包及其阶段材料，具体状态以任务包自身说明为准。
- 不再使用 `docs/临时架构/`、`docs/临时产品文档/` 或 `docs/历史/` 作为资料入口。

## 文档维护

- 根目录 `README.md` 是唯一仓库地图；新增、移动或删除资料入口时必须同步更新。
- 同一主题只能有一个当前规则源；学习资料、未来计划、任务记录和旧历史不得自称当前强制规则。
- 用户在多轮讨论中确认会影响后续产品、字段、流程或评估口径的计划时，应在同一轮新增或更新 `docs/已讨论功能/` 中的对应文档。
- 代码枚举、Schema、主题 token 和接口字段以代码为准；文档说明职责和入口，不复制维护第二份完整定义。
- 不在持久文档中混入 `//` 形式的临时 AI 指令。
- 不创建或保留 `.gitkeep`；需要的目录由代码或工具按需创建。
