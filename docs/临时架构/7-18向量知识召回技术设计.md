# 向量知识召回技术设计

> 更新日期：2026-07-19
> 状态：阶段 02 独立向量能力已实现并完成真实索引、三次专项评测；阶段 03 融合为 `HOLD_HYBRID_QUALITY`
> 适用范围：单本小说知识库的独立向量召回能力

## 一、已确认边界

- 阶段 02 必须新增一条真实、可重建、可评测的向量召回能力。
- 向量召回与现有 `mongo_lexical` 词法召回并行存在，不替换词法召回。
- 阶段 02 不做词法与向量融合；混合策略、影子流量和生产灰度属于阶段 03。
- 向量效果暂时不理想不等于删除能力，应保留独立链路、定位问题并继续优化。
- 当前生产默认仍为 `mongo_lexical`，本次基础设施配置没有改变任何生产消费者的结果。

## 二、最终选型

| 职责 | 选型 | 固定版本或标识 | 选择理由 |
|---|---|---|---|
| 向量数据库 | Qdrant Server（Docker） | `qdrant/qdrant:v1.18.3` | 独立服务、Windows 本机可运维、支持过滤与可重建集合，不把索引混进 MongoDB 事实存储 |
| Python 客户端 | `qdrant-client` | `>=1.18,<2`，当前锁定 `1.18.0` | 直接使用官方客户端并通过应用层 Protocol 隔离，不把业务绑定到 LangChain |
| Embedding 模型 | Qwen3-Embedding-4B-GGUF | `Q4_K_M`，2560 维 | 中文和多语检索能力强，4B 量化后适合当前 RTX 4080 SUPER 本机运行 |
| 推理服务 | llama.cpp | `b10066` Windows Vulkan x64 | 本地 GPU 加速，提供 OpenAI 兼容 `/v1/embeddings` 接口，无需云端模型 API |

没有采用以下方案：

- 不采用云端 Embedding API：避免正文或知识文本离开本机，消除逐次调用费用和外部可用性依赖。
- 不采用 MongoDB Atlas Vector Search：当前 MongoDB 是本机 standalone，没有 Atlas Search / `mongot` 运行条件；也要保持 MongoDB 只承担结构事实源职责。
- 不采用仓库内 JSON 精确余弦索引作为正式后端：用户已确认要把 Qdrant 作为长期向量能力基础，避免后续再次迁移索引存储。
- 不让 Qdrant 反向成为事实源：Qdrant 中的集合可以整库删除并从 MongoDB `lifecycle=confirmed` 卡片重建。

## 四、启动与运行配置

根目录 `start.bat` 统一执行五步：

1. 启动或复用 MongoDB。
2. 启动或复用 Qdrant；Docker Desktop 未运行时自动拉起。
3. 启动或复用本地 Qwen Embedding 服务，并核对模型 ID。
4. 清理后端 8000 和前端 3000 固定端口。
5. 启动并检查太初前后端。

Qdrant 和 Embedding 是本机基础服务，关闭前后端命令窗口不会主动停止它们；下一次运行 `start.bat` 会健康检查并复用。所有路径、端口、版本和模型参数由根目录 `.env` 配置，公开模板位于 `.env.example`。

## 六、已实现链路与继续约束

阶段 02 已形成以下链路：

1. `EmbeddingGateway` 与 `VectorIndexBackend` 应用层 Protocol。
2. confirmed 知识卡的身份、摘要和类型字段三类可追溯投影。
3. Qdrant 物理集合、active alias、校验清单、快照哈希和全量重建命令。
4. 只供专项评测显式调用的 `knowledge_vector` 后端。
5. Embedding 与索引检索脱敏遥测，以及同一60题的词法/向量对比。
6. 单类型关系问句锚点消歧、精确身份约束和未确认事实拒绝策略。

任何 Qdrant 命中都必须按 `card_id` 回读 MongoDB 当前卡，再校验 `lifecycle=confirmed`、更新时间和删除状态。索引缺失、损坏、模型维度变化或快照过期必须返回可分类错误；不得静默把随机向量、哈希向量或旧卡当成有效结果。

生产 `retrieval_service` 仍只注册 `mongo_lexical`。向量后端只存在于召回专项评测运行实例；阶段03在融合门禁重新达标前不得开始影子或灰度接入。
