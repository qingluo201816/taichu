# 统一知识召回第一版实施与知识沉淀工作流影响报告

> 更新日期：2026-07-13
>
> 本文是本次实施完成后的历史快照，用于追溯变更背景、验证结果和当时风险，不作为当前强制规则源。当前行为必须以代码、`AGENTS.md` 和 `project_assets/readme.md` 为准。

## 一、实施结论

本次完成了一个统一、只读的知识召回能力。写作区单步任务、章节摘要和知识沉淀 Workflow 不再分别直接读取已确认知识，而是统一调用 `RetrievalService`；未来通用 Agent Runtime 可以通过 `retrieve_knowledge` Tool 使用同一能力。

本次没有新增公共 HTTP 召回接口。“Retrieval API”在第一版中指应用层稳定调用契约，不等于 REST 接口。

三类执行体系只共享召回请求、结果和技术观测契约，不共享业务日志、状态机和评测模型：

- 写作区继续保存自己的 `WritingAIRun`。
- 知识沉淀继续保存自己的 Agent Run、节点记录、候选审核项和效果评测。
- 未来通用 Agent Runtime 仍应建立独立运行轨迹。
- 召回层通过 `retrieval_id`、调用方类型、业务运行 ID 和节点名称提供技术链路关联。

## 二、本次实现范围

第一版统一召回支持三种读取模式：

- 相关性召回：根据任务输入和辅助上下文，对已确认知识卡进行确定性词法排序。
- 身份匹配：按知识类型、名称和别名查找已有已确认知识卡。
- 有效知识快照：为固定 Workflow 节点提供已确认知识索引。

统一召回层负责：

- 固定第一版事实范围，只允许读取 `confirmed_knowledge`。
- 再次校验知识卡必须为 `lifecycle=confirmed`。
- 类型过滤、稳定排序、条数上限和字符预算。
- 返回统一结果、命中原因、候选数、截断状态和召回关联 ID。
- 把技术记录追加到 `project_assets/derived/retrieval/calls.jsonl`。
- 技术记录只保存查询长度和 SHA-256，不保存正文、完整用户输入或命中关键词原文。

本次没有实现：

- 向量索引、Embedding、混合召回或 Agentic RAG。
- 通用 Agent Runtime、运行时记忆、模型路由或 checkpoint/resume。
- 工具与子 Agent 的新一代统一调用协议；知识召回 Tool 暂时接入现有 Tool 插件协议。
- 统一三类业务运行日志、监控页面或评测模型。

## 三、对知识沉淀 Workflow 的直接影响

### 1. 运行依赖发生变化

知识沉淀 Agent 的必需能力由 `knowledge_repository` 改为 `retrieval_service`。Workflow 不再知道 MongoDB 仓储的具体读取方法，只依赖应用层召回能力。

知识写入没有跟随改变。作者确认候选后，创建或更新知识卡仍由 `KnowledgeService` 执行，AI 仍不能直接写入 MongoDB。

### 2. 候选质量闸门改走身份召回

`CandidateQualityGateNode` 判断一个实体分组是否已经存在有效知识卡时，改为调用身份匹配模式。

身份匹配底层仍委托原 MongoDB `search_confirmed_identity()`，继续使用同类型知识卡的规范化名称和别名进行精确匹配。因此本次改动没有引入模糊匹配、向量相似度或模型判断，已有知识命中语义保持不变。

影响结果：

- 命中已有卡时，仍可进入更新候选路径。
- 未命中时，仍按原质量规则判断是否接受新候选。
- MongoDB 查询失败时，节点仍会失败并由原 Workflow 错误机制处理；新增的区别是失败前会留下召回技术记录。

### 3. 实体专家的有效知识索引改走快照召回

`EntityExpertNode` 原来直接加载全部已确认知识卡，再把 `id`、类型、名称、别名和摘要渲染到 Prompt。现在改为通过有效知识快照模式取得同样字段，Prompt 数据结构没有改变。

第一版新增了两个预算边界：

- 快照最多返回 200 张知识卡。
- 默认内容预算为 50000 字符。

当前真实 MongoDB 冒烟测试的已确认候选数量低于该上限，没有发生截断。未来知识卡超过上限或单卡内容明显增长后，实体专家看到的有效知识索引可能不再是全量；届时需要根据召回技术记录中的 `truncated`、候选数和命中数判断是否调整预算、增加分类型快照或切换检索策略。

### 4. 已有知识匹配改走身份召回

`MatchExistingKnowledgeNode` 对规范化候选执行已有知识匹配时，改为调用身份匹配模式。命中后仍设置：

- `target_card_id`；
- `matched_card_name`；
- `match_reason`；
- 外部冲突信息。

候选动作仍由原有规则决定，创建卡、更新卡、冲突和忽略的业务定义没有改变。

### 5. 批量知识沉淀同步接入

批量章节分支合并后的已有知识匹配同样改走身份召回，避免单章 Workflow 和批量 Workflow 使用不同知识读取入口。

当前单章 Workflow 发起的召回记录会关联 Agent `run_id` 和具体节点名称。批量合并阶段已经记录调用方和阶段名称，但当前还没有把批量运行 ID 传入召回上下文；这不影响召回结果，但会降低跨日志定位批量调用时的便利性，属于后续观测完善项。

## 四、保持不变的 Workflow 行为

统一召回改动本身没有改变以下内容：

- LangGraph 节点拓扑和执行顺序。
- 章节读取、正文切分、通用抽取、实体聚合和专家分发逻辑。
- 角色专家、实体专家、事件规则专家的职责边界。
- 候选知识卡 Schema、已废弃字段校验和生命周期规则。
- 内部冲突检查、外部冲突检查和候选动作判定。
- JSON 中间态、作者审核、确认、拒绝和写入 MongoDB 的流程。
- 知识沉淀 Agent 自己的节点监控、运行记录和效果评测。
- LLM 模型选择、Prompt 输出解析和失败重试机制。

因此，这次不是对知识沉淀 Workflow 的重新编排，而是把其中“读取已有知识”的横切能力抽离成统一召回基础设施。

## 五、可观测性影响

知识沉淀每次调用统一召回后，会独立记录：

- `retrieval_id`；
- `consumer_type=knowledge_workflow`；
- 单章运行 ID（可取得时）；
- `CandidateQualityGateNode`、`EntityExpertNode`、`MatchExistingKnowledgeNode` 或批量匹配阶段名称；
- 召回模式、策略、候选数、命中数、截断状态和耗时；
- 命中知识卡 ID、排名和脱敏后的命中原因类别；
- 失败类型和脱敏错误。

召回技术记录不会写入知识沉淀的 `AgentRun` Schema，也不会进入知识沉淀效果分数。这样保留了两层观测边界：

- Agent Run 回答“知识沉淀流程执行得怎么样”。
- Retrieval Trace 回答“某个节点读取知识时发生了什么”。

召回技术记录写入失败不会让知识沉淀任务失败；召回结果会继续返回。当前 Workflow 没有把这类技术观测警告展示到任务监控页面。

## 六、效果与性能判断

### 正向影响

- 事实范围更安全：仓储查询和召回服务形成双重 `confirmed` 守卫。
- 单章与批量流程使用同一知识读取语义。
- 后续接入向量或混合召回时，可以替换或组合 `RetrievalBackend`，不需要再次改写 Workflow 节点。
- MongoDB 异常、空结果、候选数量、截断和耗时开始具备独立审计记录。
- 召回策略不再散落在页面服务和 Workflow 节点中。

### 当前代价与风险

- 第一版相关性召回仍会读取全部已确认知识卡后在内存中排序，不是面向大规模知识库的最终实现。
- 每次召回会追加一条 JSONL 技术记录，知识沉淀一次运行包含多次身份匹配，因此会增加少量本地磁盘写入和观测数据量。
- 实体专家快照新增 200 条和字符预算限制，知识库增长后必须监控截断。
- 当前身份召回保持精确名称/别名匹配，不会解决同义表达、间接指代和语义相关知识的召回问题。
- 召回效果还没有独立离线评测集；向量 RAG 的收益评测仍属于后续独立任务。

## 七、验证结果

实施完成时执行并通过：

- 全量测试：`uv run pytest -q`，273 项测试和 23 个子测试通过。
- 全仓 Ruff：`uv run ruff check .` 通过。
- 本次涉及的召回、写作区、章节摘要、知识沉淀和装配文件 Mypy 检查通过。
- `start.bat` 成功清理并重新启动固定端口。
- 后端 `http://127.0.0.1:8000/api/knowledge/types` 返回 200。
- 前端 `http://localhost:3000/knowledge` 返回 200。
- 真实 MongoDB 冒烟验证完成：有效知识快照可读，使用实际知识卡名称进行相关性召回时目标卡排在首位，技术观测中不包含原始查询文本。

实施时全仓 Mypy 仍有 `tests/unit/application/evaluations/test_matching.py` 中两处与本任务无关的测试类型问题；不影响本次召回实现和运行验证。

## 九、最终判断

本次改动没有把知识沉淀 Workflow 改造成通用 Agent Runtime，也没有改变它作为“按章节、预定义多步骤、产出候选并等待作者确认”的定位。

它产生的核心变化是：知识沉淀 Workflow 不再拥有自己的知识读取实现，而是成为统一召回能力的一个消费者。当前身份匹配结果与原实现保持一致，同时获得了统一范围守卫、预算控制、失败记录和后续替换召回后端的扩展入口。
