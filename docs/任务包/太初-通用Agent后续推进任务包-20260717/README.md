## 一、这份任务包解决什么问题

用户给出的八项计划方向是正确的，但与当前 `master` 的真实代码状态存在明显时间差。统一召回第一版、Tool/专业子 Agent 协议、通用 Runtime、异步动态 DAG、作者工作台、独立节点监控、确定性效果评测，以及 checkpoint/resume 第一版都已经落地。

因此，本任务包不再把这些能力按“从零建设”重复安排，而是把推进路线修正为：

1. 先冻结真实基线并补齐评测地基。
2. 把统一召回从“已能用”推进到“可比较、可配置、可灰度”。
3. 将向量 RAG 保持为独立实验能力；只有稳定优于词法基线才进入生产。
4. 在统一召回之上接入混合召回，并保留一键回退。
5. 建设通用 Agent 专属运行时记忆与上下文压缩。
6. 把现有静态模型角色映射升级为可审计的自适应模型路由。
7. 强化现有 checkpoint/resume，重点解决崩溃窗口、外部副作用不确定性和长链路稳定性。
8. 在真实运行数据上建立语义评测、人工校准和长期运行经验闭环。
9. 最后进行业务收口、灰度、治理和文档清理。

## 三、任务包结构

- `仓库事实快照.md`：当前代码事实、已完成能力、真实缺口和风险。
- `修正后的推进路线图.md`：阶段顺序、依赖、晋级门禁和失败分支。
- `任务执行总规约.md`：所有阶段共同遵循的架构、数据、测试和文档规则。
- `任务索引.json`：机器可读的阶段、依赖、任务编号和状态。
- `phases/`：九个可执行阶段任务。
- `prompts/连续执行总提示词.md`：可直接交给 Codex 的连续执行提示词。
- `prompts/单阶段执行提示词模板.md`：只执行某个阶段时使用。
- `templates/`：验收、评测、ADR、故障注入记录模板。
- `scripts/check_repository_baseline.py`：检查仓库、分支、基线漂移和关键路径。
- `scripts/validate_task_pack.py`：检查任务包文件和任务索引完整性。
- `checksums.sha256`：任务包内文件校验和。

## 四、推荐用法

先在太初仓库根目录运行：

```bash
python <解压目录>/scripts/check_repository_baseline.py
```

若 HEAD 不等于任务包基线，不要机械套用旧文件路径。先按阶段 00 重新审计差异；确认新提交没有改变职责边界后，再使用 `--acknowledge-drift` 继续。

连续推进时，把 `prompts/连续执行总提示词.md` 和当前阶段文件交给 Codex。Codex 必须在每个阶段结束时完成自检、记录测试和评测结果，然后自动进入下一个依赖已满足的阶段。以下情况属于硬阻断，必须停止相关晋级而不是伪造成功：

- 违反 Markdown / MongoDB 唯一事实源边界。
- 向量方案没有真实 Embedding 能力或未达到收益门禁。
- 任何写操作绕过作者授权、幂等或冲突保护。
- 全量测试、类型检查、前端构建或固定端口启动验证失败。
- 基线漂移导致任务假设失效。
- 发现密钥、完整 Prompt、正文原文或外部页面全文被写入技术遥测。
- 故障注入出现重复写入、静默覆盖或无法辨识的副作用。

某个实验阶段未达到晋级门禁时，应产出明确的 `NO-GO` 报告并保留词法召回或静态路由等稳定路径；不应为了“完成路线图”强行上线实验能力。其他与该失败项无直接依赖的阶段可以继续。
