## 一、当前架构与数据事实

太初是单本玄幻小说个人写作助手。运行期间只有一个小说上下文，不设计小说选择、`project_id`、多租户或跨小说检索。

当前三类执行体系必须继续分开：

1. 写作区单步任务：一次明确任务，快速返回，可使用统一召回。
2. 正文知识沉淀 Workflow：固定章节流程、候选知识草稿、作者审核，继续使用自己的运行记录和评测。
3. 通用写作助手 Runtime：开放式任务、高层规划、动态 DAG、工具与专业子 Agent 编排、人工中断、恢复和结果收敛。

它们可以共享统一召回、LLM 网关、存储契约和脱敏技术遥测，但不得合并业务状态机、业务日志、监控模型和效果评测。

数据边界：

- 正文 Markdown 是唯一文本事实源。
- MongoDB `taichu.knowledge_cards` 中 `lifecycle=confirmed` 的卡片是唯一结构事实源。
- 向量索引、缓存、图谱、运行记录、评测和记忆都不是小说事实。
- AI 不得直接写 MongoDB；任何正文或结构化事实写入都必须经过确定输入、校验、作者授权和应用服务。
- `project_assets/source/knowledge/` 已完成迁移并删除，禁止重建或双写。
- SQLite/FTS 已废弃，禁止重新引入。
- 所有非事实持久数据必须显式使用 `draft|confirmed|rejected` 生命周期。

## 二、当前代码入口

### 统一召回

- 稳定请求、结果和遥测模型：`src/taichu/application/retrieval/models.py`
- 跨层协议：`src/taichu/application/contracts/retrieval.py`
- 统一召回服务：`src/taichu/application/services/retrieval_service.py`
- MongoDB 确定性词法后端：`src/taichu/infrastructure/retrieval/mongo_lexical_backend.py`
- JSONL 召回遥测：`src/taichu/infrastructure/retrieval/jsonl_trace_repository.py`
- Agent 召回 Tool：`src/taichu/application/tools/knowledge_retrieval/`

当前 `RetrievalMode` 有 `relevance`、`identity`、`catalog`。服务负责 top-k、字符预算、`lifecycle=confirmed` 二次守卫、结果标准化、查询哈希和技术遥测。当前相关性召回仍会加载已确认卡后在内存中执行确定性词法排序；服务构造时只注入一个后端，尚无向量、混合、影子评测或策略路由。

### Tool 与专业子 Agent

当前已有 16 个真实生产 Tool 和 12 个真实专业子 Agent。能力层已经具有：

- 独立 ToolManifest / SubagentManifest。
- 输入输出 Schema。
- 最小权限、外部访问许可和作者写入授权。
- 超时、重试、幂等键和调用预算。
- `task_id`、`run_id`、`call_id`、`parent_call_id` 形成的调用树。
- Tool、子 Agent、LLM 三层脱敏调用记录。
- `lifecycle=draft` 的有类型中间产物和来源引用。
- 静态逻辑模型角色映射。

不得再为验证后续 Runtime 新增假 Tool、假 Agent 或测试专用执行器。

### 通用 Runtime

- 运行模型：`src/taichu/application/general_agent/models.py`
- 高层编排：`src/taichu/application/general_agent/orchestrator.py`
- 动态 DAG：`src/taichu/application/general_agent/executor.py`
- 顶层 LangGraph、生命周期和恢复：`src/taichu/application/general_agent/service.py`
- 检查点协议：`src/taichu/application/contracts/general_agent_run.py`
- JSON 检查点仓储：`src/taichu/infrastructure/general_agent_runs/json_repository.py`
- API：`src/taichu/api/routes/general_agent.py`
- 组装：`src/taichu/main.py`

当前能力包括直接回答、澄清、动态计划、无环依赖校验、异步并行、上游字段绑定、中间产物传递、写入授权、有限重规划、取消、超时、恢复和 NDJSON 事件。

当前默认限制：

- 最大计划节点数：12，可配置上限 40。
- 最大重规划次数：1，可配置上限 3。
- 默认并发：3，可配置上限 8。
- 默认总 Tool 调用上限：40，可配置上限 100。
- 默认运行时限：900 秒，可配置上限 7200 秒。

当前运行模型会保存完整 `messages`、节点 `resolved_input`、节点 `output`、来源、中间产物和错误；编排 Prompt 会读取全部对话、上一版计划和节点结果。尚无上下文预算装配器、记忆检索或压缩摘要。

### checkpoint / resume

现有仓储把每次运行保存为 `project_assets/derived/general_agent_runs/<run_id>.json`，通过临时文件替换实现最新快照原子更新。`checkpoint_revision` 会递增，但旧修订不会保留。

Runtime 会在生命周期变化、计划生成、DAG 准备、节点开始、节点完成、人工等待、校验和失败时保存最新状态。服务重启后会把活动任务封存为可恢复失败状态，将运行中节点复位为安全状态；成功节点不会普通重跑。写 Tool 通过正文哈希、结构版本、知识更新时间和幂等键降低重复副作用风险。

真实缺口不是“有没有恢复”，而是：

- 最新快照没有修订历史和校验链。
- 外部写入成功、节点完成检查点尚未保存的窗口仍可能产生不确定结果。
- 没有系统化故障注入矩阵。
- 没有测量最大稳定节点数、任务长度成功率、恢复成功率和并发边界。
- 恢复时尚未冻结未来的记忆、召回策略和模型路由决策。

### 模型能力

当前已经有 Right Code 统一多模型网关、模型目录、普通与流式调用、结构化输出、Token/费用/耗时遥测和模型监控。`ModelRoleRouter` 当前只是：

```text
逻辑角色 -> 显式覆盖模型；否则使用默认模型
```

它没有按任务风险、上下文长度、质量基准、费用、延迟、模型健康、失败类型或历史评测做自适应决策。因此后续“模型路由”应建设策略层，而不是重新搭供应商适配层。

### 节点监控与评测

通用 Runtime 已有独立节点监控，可查看动态 DAG、计划修订、节点详情、生命周期和脱敏调用树。

通用 Agent 也已有独立五维确定性评测：

- 任务完成度。
- 能力选择与路径。
- 权限与安全边界。
- 执行健康度。
- 答案覆盖度。

当前核心评测集有 8 个样例。创作类文风、叙事张力和文学质量只提供确定性检查与人工复核提示，尚无经过人工校准的独立语义裁判。

## 四、基线漂移处理

任务包内具体文件路径按基线提交核对。执行时若 HEAD 已变化：

1. 先运行 `scripts/check_repository_baseline.py`。
2. 阅读新增提交与相关文件。
3. 更新阶段 00 的事实清单和测试基线。
4. 若职责边界未变，可继续使用任务编号；文件落点按新代码调整。
5. 若新提交已经实现某阶段，标记该阶段为“已由仓库吸收”，只执行回归与缺口复核。
6. 不得为了匹配任务包而回退仓库中更成熟的实现。
