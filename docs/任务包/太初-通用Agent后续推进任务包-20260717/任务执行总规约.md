# 任务执行总规约

> 更新日期：2026-07-17  
> 适用于本任务包全部阶段。

## 一、执行前必读顺序

每次开始阶段前，必须读取当前仓库中的：

1. `AGENTS.md`
2. 当前阶段涉及 `docs/` 时读取 `docs/rule.md`
3. 涉及 `.agents/skills/` 时读取 `.agents/skills/rule.md`
4. 涉及 `web/` 时读取 `DESIGN.md`
5. 涉及 `web/` 时自动读取 `.agents/skills/taichu-ui-components/SKILL.md`
6. `project_assets/readme.md`
7. 当前阶段列出的代码入口和上一阶段验收记录

任务包只提供基线，不得压过仓库内更新后的规则。

## 二、不可变架构边界

- 运行态代码只放 `src/`、`web/`。
- 开发辅助规则和 Skill 只放 `.agents/`；Codex 原生自定义 Agent 与客户端配置只放 `.codex/`。
- 单本小说数据只放 `project_assets/` 或 MongoDB 指定事实源。
- `domain` 不依赖 Agent、LangGraph、LLM、MCP、MongoDB、文件系统或向量库。
- 跨层行为契约优先使用 `typing.Protocol`。
- 插件发现归基础设施层，协议校验、注册和查询归应用层。
- 新增专业 Agent 只能新增插件目录并实现协议，不修改已有注册逻辑。
- Tool、专业子 Agent、知识沉淀 Workflow 和通用 Runtime 不得塞入一个混合注册中心。
- Node 是编排状态边界，不等于 Agent；普通 Tool 调用默认是节点内调用记录。
- 不以“当前简单”或“以后再拆”为理由合并已明确不同的职责。

## 三、事实与派生数据边界

- Markdown 是唯一文本事实源。
- MongoDB 已确认知识卡是唯一结构事实源。
- 向量索引、记忆索引、Prompt 经验、评测、运行记录、checkpoint 和缓存都是非事实。
- 所有非事实持久记录必须有 `lifecycle=draft|confirmed|rejected`。
- AI 只能生成提案；正文和知识写入必须由应用服务完成。
- 不恢复 `project_assets/source/knowledge/`。
- 不引入 SQLite/FTS。
- 向量、记忆和经验索引必须可以由其来源重建。
- 技术遥测不得保存密钥、鉴权头、完整 Prompt、完整用户输入、完整正文或外部页面全文。
- 任何“事实摘要”进入记忆时必须携带来源引用，并在消费时可重新校验；记忆本身不是事实。

## 四、能力接入规则

### 召回

- 所有 AI 消费者继续通过 `RetrievalService` 或其稳定应用层门面读取知识。
- 向量后端、混合后端和 Agentic RAG 都是统一召回内部策略，不能新建旁路业务 API。
- 身份匹配、目录读取和指定卡片读取保持确定性，不强行向量化。
- 不为“Retrieval API”机械增加公共 REST 端点；只有明确产品消费者需要时才增加 HTTP API。

### 记忆

- 记忆是 Runtime 基础设施，不注册为可被模型任意写入的通用 Tool。
- 记忆读写由明确的策略服务控制；LLM 最多产生结构化候选。
- 检查点负责恢复执行，记忆负责跨步骤/多轮承接，运行经验负责跨任务策略学习，三者不得混为一张表或一个 JSON。

### 模型路由

- 保留现有统一 LLM 网关和模型目录。
- 模型路由只选择已注册、能力兼容的模型。
- 静态角色覆盖是硬约束；自适应路由不能偷偷覆盖用户或配置固定选择。
- 路由决策必须可回放、可解释、可禁用。

### 写操作

- 所有写 Tool 保持真实幂等、作者授权绑定、输入哈希和资源范围。
- 恢复任务时不得扩大授权。
- 外部副作用无法确认时进入对账，不允许直接重试造成重复写入。

## 五、开发与文档规则

- Python 使用 `uv`，禁止 pip、poetry、pipenv。
- Python 版本保持 `>=3.12`。
- 新增依赖前先证明现有标准库和当前依赖不能满足；必须说明 Windows 本机启动影响。
- 更换组件时同步删除旧依赖、旧配置、旧接口、旧状态、旧测试和失效文档。
- 代码内不写“v0.x”“第一版”等仅用于开发过程说明的版本；只有存储格式、协议兼容和迁移需要时才允许机器版本。
- `docs/` 中文命名并包含更新日期。
- 同一主题只有一个当前规则源；临时设计放 `docs/临时架构/`，实现报告放 `docs/历史/`，已确认产品决策更新 `docs/已讨论功能/`。
- 新增或移动资料入口时更新根 `README.md`。
- 修改 `project_assets/` 目录职责时同步更新 `project_assets/readme.md`。
- 禁止 `.gitkeep`。

## 六、前端规则

- 只交付桌面浏览器，不做手机、平板、原生 App 适配。
- 使用现有 Next.js、shadcn/ui、Base UI、Tailwind 和本地组件。
- 所有文案中文。
- 记忆、路由、恢复和评测页面保持高密度、低干扰；长日志、完整 JSON、Prompt 和原文默认折叠。
- 不增加品牌化称呼，不把 Agent 改名为“器灵”等。
- 不为新基础设施创建营销式首页或游戏化 HUD。

## 七、测试与评测规则

每个阶段必须有：

- 单元测试：模型、策略、排序、预算、状态转移和错误语义。
- 集成测试：使用真实生产 Tool/子 Agent 契约，不新增假能力。
- 兼容测试：读取旧 JSON/JSONL 和旧检查点。
- 失败测试：超时、损坏、空结果、权限拒绝、索引过期和服务重启。
- 评测：与阶段基线比较，不只证明“代码能运行”。
- 数据边界测试：不得返回未确认知识，不得把记忆当事实，不得越权写入。
- 观测测试：敏感内容不进入技术记录。
- 全量门禁：ruff、mypy、pytest、compileall、git diff check。
- 前端涉及时：lint、TypeScript、相关测试、build。
- 启动关键文件涉及时：`start.bat` 固定端口验证。

测试桩可以替代外部网络和模型响应，但生产交付证据必须至少有一次真实能力验证。不得把测试桩通过当成向量、模型或恢复能力的真实收益证据。

## 八、阶段自检格式

每个阶段结束必须按以下顺序自检：

1. 事实核对：实现是否仍符合当前 HEAD，而非任务包旧假设。
2. 范围核对：是否误改写作区或知识沉淀 Workflow。
3. 架构核对：层级、Protocol、注册和依赖方向是否正确。
4. 数据核对：事实、派生、索引、记忆、评测、checkpoint 是否分层。
5. 安全核对：作者授权、幂等、敏感信息和外部访问许可。
6. 测试核对：记录命令、结果和未执行原因。
7. 评测核对：与基线比较，列出提升、回归和置信度。
8. 回滚核对：禁用新能力后旧路径是否可用。
9. 文档核对：规则源、临时设计、历史报告和目录说明是否同步。
10. 清理核对：无旧实现、僵尸配置、孤儿依赖和 `.gitkeep`。
11. 输出阶段结论：`PASS`、`PASS_WITH_LIMITS` 或 `NO-GO`。
12. 若依赖满足且不存在硬阻断，自动进入下一阶段，不要求用户逐阶段确认。

## 九、阶段报告最少内容

- 仓库 HEAD 和工作树状态。
- 完成的任务 ID。
- 修改/新增/删除文件。
- Schema 与数据迁移。
- 配置变化。
- 测试命令和结果。
- 评测集、基线、当前结果和差异。
- 风险与已知边界。
- 回滚方法。
- 阶段结论。
- 下一阶段可用的稳定接口。

## 十、禁止事项

- 不从零重写已存在的 Runtime、Tool/子 Agent 或 checkpoint。
- 不创建假 Tool、假 Agent、假生产 Embedding 或假模型路由。
- 不直接把向量分数称为答案质量。
- 不用记忆替代 MongoDB/Markdown 事实。
- 不把通用 Runtime 业务日志塞进知识沉淀 AgentRun。
- 不把所有模型调用统一固定成一个模型后宣称完成“路由”。
- 不把历史评测结果作为当前规则源。
- 不提交密钥、真实鉴权信息或本机绝对路径。
- 未经授权不提交、不推送、不开 PR。
