## 一、阶段目标

在不改变四个现有知识 Tool 业务边界的前提下，把统一召回从“单后端可用”推进为：

- 有稳定的契约特征测试。
- 按消费者和模式可配置预算。
- 能记录请求策略、实际策略、回退与分支耗时。
- 有独立离线评测集、指标、基线和结果存储。
- 能阻止写作区、Workflow 和通用 Agent 绕过统一召回直接读取知识。
- 为阶段 02/03 的向量与混合召回提供兼容接口。

本阶段仍以 `mongo_lexical` 为唯一生产相关性后端，不提前上线向量。

## 三、架构决策

### 1. Retrieval API 的含义

继续把 Retrieval API 定义为应用层稳定调用契约，不为了名字增加公共 REST。HTTP 调试或评测端点只有在现有产品页面确有消费需求时才增加，并且不能成为业务唯一入口。

### 2. 策略与后端分层

建议新增应用层策略解析：

- `RetrievalPolicyProfile`
- `RetrievalPolicyResolver`
- `RetrievalExecutionPlan`

策略根据 `consumer_type`、`mode` 和配置解析 top-k、字符预算、超时、生产策略和回退；具体 Mongo/向量/混合执行仍由后端实现。业务消费者不得知道具体后端类。

### 3. 向后兼容

现有 `RetrievalRequest`、`RetrievalResult` 和四个 Tool 输出是兼容边界。新增字段使用默认值；旧 JSONL 技术记录必须可读。不得通过重命名现有枚举制造无必要迁移。

## 四、任务清单

### `RET-001` 建立契约特征测试

覆盖：

- `relevance` 必须有 query 或 context。
- `identity` 必须有类型、名称和别名。
- `catalog` 不接受 identity。
- 事实范围固定为已确认知识。
- top-k 和字符预算硬上限。
- 未确认卡被服务层二次过滤。
- 空结果、失败、遥测写失败的行为。
- 稳定排序和相同输入可复现。
- 查询正文不进入 trace，只保存长度和 SHA-256。
- 四个知识 Tool 仍保持独立输入输出语义。

建议测试入口：

- `tests/unit/application/retrieval/`
- `tests/integration/retrieval/`
- `tests/unit/application/tools/knowledge_retrieval/`

### `RET-002` 实现消费者级召回策略

建议新增：

- `src/taichu/application/retrieval/policy.py`
- `src/taichu/application/retrieval/execution.py`

配置建议：

- `RETRIEVAL_POLICIES_JSON`
- `RETRIEVAL_DEFAULT_RELEVANCE_STRATEGY=mongo_lexical`

第一阶段策略至少区分：

- 写作区单步任务。
- 章节摘要。
- 知识沉淀 Workflow。
- 通用 Agent Tool。
- 身份匹配。
- 目录快照。

策略配置只能调整预算、超时和后端选择，不得扩大事实范围。无效配置在启动时失败并给出中文安全错误，不得静默回退成不可预测值。

### `RET-003` 扩展可观测执行元数据

在保持旧记录可读的前提下，增加机器有用字段：

- `policy_name`
- `requested_strategy`
- `effective_strategy`
- `fallback_used`
- `fallback_reason_code`
- `backend_duration_ms`
- `post_filter_duration_ms`
- `strategy_snapshot`
- `index_snapshot_id`（当前为空，为阶段 02 预留）
- 分支级候选数、命中数和耗时的结构化列表

不得保存原始查询词、完整正文、Embedding 向量或卡片完整内容。错误原因使用枚举代码和脱敏摘要。

### `RET-004` 建立独立召回评测模型

建议新增：

- `src/taichu/application/evaluations/retrieval/models.py`
- `src/taichu/application/evaluations/retrieval/service.py`
- `src/taichu/application/contracts/retrieval_evaluation.py`
- `src/taichu/infrastructure/evaluations/retrieval/`
- `tests/fixtures/evaluations/retrieval_knowledge_core/manifest.json`

每个样例至少包含：

- `case_id`
- 查询文本和辅助上下文。
- 查询类别。
- 允许的知识类型。
- `relevant_card_ids`
- `must_not_return_card_ids`
- 是否应为空。
- 期望 top-k。
- 数据集生命周期和校验和。

第一批至少 60 个样例：

- 精确名称/别名：15。
- 语义改写/隐含表达：20。
- 状态、关系、事件和规则：15。
- 多实体消歧：5。
- 无答案/对抗查询：5。

评测指标：

- Recall@1/3/5/10。
- Precision@k。
- MRR。
- nDCG@k。
- 空结果准确率。
- 禁止卡命中率。
- 平均和 p95 延迟。
- 候选数、截断率和字符预算命中率。

评测结果存入 `project_assets/derived/agent_evaluations/retrieval/`；同步更新 `project_assets/readme.md`。

### `RET-005` 固化词法基线

运行当前 `mongo_lexical`，冻结：

- 数据集校验和。
- Mongo 已确认卡快照标识。
- 策略配置。
- 每个指标和分组指标。
- 失败样例。
- 运行环境和耗时。

基线报告放入：

`docs/历史/<日期>-统一知识召回评测基线报告.md`

不得为提高基线而删除难题；失败样例是阶段 02 的主要输入。

### `RET-006` 增加绕过统一召回的防回归检查

建立静态或测试期检查，禁止 AI 消费者直接调用：

- `list_confirmed_cards`
- `search_confirmed_identity`
- Mongo 查询实现

允许的例外必须显式列出，例如知识管理 CRUD、索引重建和召回基础设施本身。检查应针对职责而不是简单全仓字符串禁用，避免误伤测试和仓储实现。

### `RET-007` 评测/运维入口

优先提供命令行：

```bash
uv run python -m taichu.application.evaluations.retrieval.cli   --dataset retrieval_knowledge_core   --strategy mongo_lexical
```

只有现有监控页面需要查看时才增加只读 API。任何 API 都不得返回完整知识卡正文或查询正文之外的敏感内容。

## 五、测试重点

- 不同消费者解析不同策略，但事实范围相同。
- 非法策略配置启动失败。
- JSONL 旧记录兼容。
- Trace 写入失败不影响召回结果。
- Mongo 故障有失败 trace。
- 评测结果校验和稳定。
- 同一快照重复运行排序一致。
- 直接读取防回归测试能捕获新旁路。
- `identity` 与 `catalog` 行为不受后续策略字段影响。
