# Codex SDD Skill 编排规范

## 一、职责模型

Codex SDD 采用“主 Agent 编排 + 专责 Agent 执行 + 独立 Agent 校验”的结构。

- 主 Agent：维护完整目标、读取状态、选择下一阶段、传递上游产物、核对收尾、登记状态、组织修复。
- 生成 Agent：只生成本阶段目标产物，不推进全局状态，不判定自己的产物 PASS。
- 评审 Agent：对差距、设计质量或实现质量做限定范围评审，不越权生成。
- 独立校验 Agent：隔离上下文、先发现再对比、只写发现与报告，不修复目标。
- 状态脚本：提供确定性的状态更新、任务进度、对象哈希、日志和恢复能力。

编排器不能以“我已经理解子角色”作为跳过子 Agent 或规则文件的理由。各阶段的命令、Agent、规则、模板均是执行契约的一部分。

## 二、默认自动推进

本项目默认全自动，不在正常阶段间请求批准。每个阶段结束后，主 Agent完成收尾检查并立即进入下一个已授权阶段。

### 自动推进信号

同时满足以下条件即推进：

1. 当前阶段的必需产物存在、非空、结构可解析。
2. 当前阶段的机械门禁与判断门禁均通过。
3. 需要独立校验的阶段存在当前对象哈希对应的 PASS 报告。
4. 状态脚本成功登记阶段且 `state.py validate` 通过。
5. 下一阶段属于用户最初授权的目标范围。

### 必须暂停的边界

只有以下情况暂停并询问用户：

- 原始描述、项目事实或高优先级规则之间存在会改变需求边界的冲突，无法通过仓库调查消除。
- 下一步需要用户未授权的业务代码实现、外部发布、远程写入、重要业务数据删除或其他明显扩大范围的动作。
- 同一独立门禁经过两轮定向修复仍 FAIL。
- 工作树存在与本任务重叠、无法安全保留的用户改动。
- 必需输入不在仓库且只有用户能提供。

“进入下一阶段”“文档已生成”“建议先审阅”不是暂停理由。

## 三、启动与恢复

### 新流程

1. 解析 `operation`、`spec_id`、原始描述和目标阶段。
2. 读取根 `AGENTS.md`、`README.md` 及相关强制规则。
3. 执行 `state.py init`。
4. 执行 `state.py validate`。
5. 从 `initialized` 开始运行阶段循环。

### 恢复流程

1. 执行 `state.py show --spec <id>`；未指定规格时只使用 `.sdd/state.json` 中合法的 `active_spec`。
2. 执行 `state.py validate --spec <id>`。
3. 核对已登记产物实际存在且对象哈希未失效。
4. 读取 `target_phase`，确定原定终点。
5. 从第一个不满足门禁的阶段恢复，而不是从聊天摘要推断。
6. 若索引漂移，先运行 `repair-index`，再重新验证。

状态文件是恢复事实源；对话计划只是当前视图，不能覆盖磁盘状态。

## 四、阶段循环

### 全自动链路

每个 Step 严格执行：

```text
读取当前状态
→ 加载命令定义、Agent 定义、规则、模板与允许的上游产物
→ 委派专责 Agent
→ 接收结构化结果
→ 核对收尾检查
→ 需要时调用独立校验
→ FAIL 时定向修复并重跑门禁
→ 通过状态脚本登记
→ state.py validate
→ 自动进入下一已授权 Step
```

不得先登记状态再补产物；不得在独立校验前把阶段标记为“已校验”。

## 五、统一收尾检查单

每个子 Agent 返回前必须输出：

```text
【Step 收尾检查】
- [x/ ] 输入规格与目录匹配
- [x/ ] 必读规则、上游产物和项目事实已读取
- [x/ ] 预期产物已生成且非空
- [x/ ] 未写入禁止文件
- [x/ ] 需求/设计/任务追踪完整
- [x/ ] 机械检查通过
- [x/ ] 判断门禁通过
- [x/ ] 实际证据与命令已记录
- [x/ ] 未决项已区分“风险”和“阻塞”
结论：全部完成 | 未完成
```

主 Agent不得只相信摘要，必须实际检查：

- 文件存在性与非空；
- 必需标题、表格、结论字段；
- 数字需求 ID 的全覆盖；
- 目标文件 SHA-256 与报告记录一致；
- `tasks.md` 与 `tasks-status.json` 的任务 ID 一致；
- `state.py validate` 返回成功。

未完成项优先退回当前角色修复，不推进。

## 六、阶段专属收尾

| Step | 必查项 |
|---|---|
| 初始化 | `spec.json`、初始 `requirements.md`、`progress.log`；规格标识为两段 |
| 需求 | 资产探查、数字需求 ID、每项至少一个 EARS 验收标准、无实现细节、需求草稿门禁通过 |
| 需求独立校验 | discovery 先于目标读取；报告含哈希、证据、问题分级、追踪表和精确结论 |
| 差距分析 | 现状、需求到资产映射、多个可行方案、未知项、风险；无工时或排期 |
| 设计 | `research.md`（需要时）、边界承诺、文件规划、组件契约、需求追踪、测试与迁移 |
| 设计评审 | 最多三个关键问题、GO/NO-GO、需求追踪和设计证据 |
| 设计独立校验 | discovery、当前对象哈希、真实接口/文件/依赖证据和精确 PASS/FAIL |
| 任务 | 所有需求与组件有任务；单一可验证结果；依赖和边界明确；并行标记安全 |
| 实现 | 测试先行证据、受影响回归、旧实现清理、任务状态、实现报告 |
| 实现验证 | 实际 diff、测试命令与结果、启动约束、清理、手工验收、精确 PASS/FAIL |

## 七、自动修复循环

### 文档阶段

1. 独立校验返回 FAIL。
2. 主 Agent提取每个 critical/major 问题和对应证据。
3. 只把问题清单、目标产物和允许上游产物交回原生成角色。
4. 生成角色只修复报告指出的问题，同时重新运行自身草稿门禁。
5. 重新创建独立校验上下文；不得让原校验上下文在读过目标后继续充当“先发现”。
6. 最多两轮。第三次仍不通过则写入阻塞原因并暂停。

### 实现阶段

1. 实现验证 FAIL 时，根据失败类型回到最小责任范围：测试、实现、设计或需求。
2. 如果发现设计本身错误，先使下游校验失效，再返回设计阶段。
3. 修复后重新运行相关测试与完整实现验证。
4. 不通过删除测试、放宽断言或把必需任务改成可选来制造 PASS。

## 八、持久化任务树

Codex SDD 不依赖会话内任务对象。任务树由以下文件组成：

```text
.sdd/state.json                         # 规格索引和活动规格
.sdd/specs/<id>/spec.json               # 阶段、目标、校验和阻塞
.sdd/specs/<id>/tasks.md                 # 计划任务
.sdd/specs/<id>/tasks-status.json        # 每个任务的执行状态和证据
.sdd/specs/<id>/progress.log             # 只追加审计事件
```

### 状态更新

- 阶段开始：读取状态并记录执行意图；不提前推进 phase。
- 任务开始：`task-set --status in_progress`。
- 任务完成：验证通过后 `task-set --status completed`，同时记录变更和验证证据。
- 任务失败：保留待办或标记失败/阻塞信息，不伪造完成。
- 阶段完成：`advance` 或 `validation`。
- 全局阻塞：写入 `spec.json.blocker` 的结构化说明。

### 恢复保证

- `tasks-status.json` 与 `tasks.md` 按稳定数字 ID 对齐。
- 已完成任务不得因上下文压缩重新执行；先核对现有代码和证据。
- 产物变化使相应校验哈希失效，恢复时必须重新校验。
- 日志不可作为状态真相反向覆盖 `spec.json`，仅用于审计。

## 九、并行规则

并行只用于独立、边界不重叠的调查或实现任务。以下工作不得并行：

- 同一目标文档的生成与校验；
- 独立发现阶段与目标文档读取；
- 依赖上游结论的设计综合；
- 写入同一文件、同一状态对象或共享可变资源的任务；
- 需要按顺序形成证据链的 RED/GREEN/REFACTOR。

即使 `tasks.md` 标记 `(P)`，主 Agent仍须在执行时复核当前工作树是否产生新的冲突。

## 十、异常处理

| 场景 | 处理 |
|---|---|
| 输入缺失 | 先从项目事实查找；只有用户独占信息缺失时暂停 |
| 子 Agent 失败 | 保留状态不推进，记录实际错误，按同一职责重试 |
| 子 Agent 只返回摘要 | 视为未完成，要求补齐产物和收尾检查 |
| 规则或模板缺失 | 框架损坏，停止；不得内联降级 |
| 校验对象在校验中变化 | 报告无效，重新发现并校验 |
| 测试命令不明确 | 从项目配置和现有 CI/README 查明；仍未知则明确限制，不声称 PASS |
| Graphify 不可用或图谱范围不含目标 | 使用 `rg`、源码、测试和配置降级，并在证据中说明 |
| 工作树有无关改动 | 保留并绕开；不要回滚、覆盖或纳入本阶段产物 |

## 十一、完成定义

自动流程只有在目标阶段的全部状态证据和门禁满足时完成。最终回复必须说明：

- 达到的规格阶段；
- 生成/更新的关键产物；
- 独立校验结论与对象哈希；
- 实际执行的验证；
- 未完成项或真实风险；
- 未经用户授权而有意未执行的范围（例如业务实现）。

不得把“已生成文档”“子 Agent 返回成功”或“计划已列完”等同于流程完成。

## 原编排规范的逐节保真映射

本节记录原 `SKILL_ORCHESTRATOR_PATTERN` 的每一组约束在 Codex 中的落点。原规则与太初已确认决策冲突时，
保留约束目的并替换运行机制，不保留会误导执行的旧示例。

### 一、子 Agent 执行机制

原规范要求编排器只管理流程，每一步创建隔离的子 Agent，子 Agent 只执行被分配的工作，并以结构化结果返回。
本文件保留为：

- 主 Agent 始终持有目标、阶段、依赖和推进权；
- 每个阶段加载命令、Agent、规则、模板与允许的上游产物；
- 生成、评审和独立校验使用不同职责与上下文；
- 子 Agent 不推进全局状态，也不越权执行相邻阶段；
- 返回必须含状态、产物、证据、问题和收尾检查；
- 主 Agent 实际检查文件和状态，不能只相信“成功”摘要。

对应落点：第一章“职责模型”、第四章“阶段循环”和第五章“统一收尾检查单”。

### 二、交互确认与推进信号

原规范的交互菜单、修改当前结果、重做当前步骤和退出流程仍保留为显式交互模式的行为。
按太初“默认全自动”决策适配为：

- 默认模式在门禁通过后自动推进，不弹出例行“是否继续”；
- 用户明确要求逐步确认时，只有“继续”推进到下一 Step；
- “修改当前结果”和“重新执行”都停留在当前 Step；
- “退出”只停止流程，不伪造后续完成；
- 真正的范围冲突、越权写入、两轮修复失败或用户独占输入缺失仍必须暂停。

对应落点：第二章“默认自动推进”和第十章“异常处理”。

### 三、Step 收尾检查

原规范要求每步先展示/验证检查单，未完成项必须退回修复。本文件完整保留：

- 输入和规格目录一致；
- 必读规则与上游产物已读取；
- 预期产物存在且非空；
- 未触碰禁止文件；
- 追踪、机械检查、判断门禁和实际证据齐全；
- 风险与阻塞已区分；
- 阶段专属产物与结论满足要求；
- 任一项未完成时不得推进。

对应落点：第五章“统一收尾检查单”和第六章“阶段专属收尾”。

### 四、状态追踪机制

原规范用会话内任务对象保存承诺。Codex 没有可依赖的同等会话任务系统，因此按用户决策替换为持久化任务树：

- `.sdd/state.json` 保存活动规格索引；
- `spec.json` 保存阶段、目标、校验、哈希与阻塞；
- `tasks.md` 保存计划；
- `tasks-status.json` 保存每个任务的执行状态和证据；
- `progress.log` 保存只追加审计事件；
- `state.py show/validate/repair-index` 支持上下文压缩和会话重启后的恢复。

阶段开始、任务开始、任务完成、失败和阻塞都通过状态脚本登记；不得手工伪造完成。
对应落点：第三章“启动与恢复”和第八章“持久化任务树”。

### 五、异常处理

原规范列出的输入缺失、子 Agent 失败、超时、部分结果和规则缺失场景均保留，并补充：

- 不完整结果按未完成处理；
- 状态不推进，保留实际错误；
- 可在同一职责内重试；
- 规则/模板缺失视为框架损坏，不用临时提示降级；
- 校验对象变化后报告立即失效；
- Graphify 不可用时回退到源码、测试与 `rg`；
- 无关工作树改动必须保留和绕开。

对应落点：第七章“自动修复循环”和第十章“异常处理”。

### 六、编排 Skill 模板

原模板中的名称、描述、参数、步骤列表、Step 执行、确认、错误处理和禁止事项，映射为：

1. `SKILL.md` 定义调用语法、路由和默认目标；
2. `command-calling-spec.md` 定义统一委派字段和每个操作；
3. 本文件定义阶段循环、收尾、修复、状态与恢复；
4. 各 `references/commands/*.md` 定义单阶段输入、输出和禁止项；
5. 各 `.codex/agents/*.toml` 直接内嵌对应完整 Agent 协议。

编排器仍禁止亲自替代专责 Agent、跳过步骤、同时启动有依赖的 Step、替用户作业务决策或在未完成时推进。

### 七、原规范约束的保留结论

- 子 Agent 隔离执行：保留。
- 主 Agent 等待并核验结果：保留。
- 结构化返回：保留并加强证据要求。
- 每步收尾检查：保留。
- 修改/重做不推进：保留。
- 默认每步审批：改为仅显式交互模式。
- 会话内任务对象：替换为 `.sdd/` 持久化状态。
- 工号目录和工时表：删除；个人项目不适用且项目规则禁止工时估算。
- 旧 PRD Skill 名称：替换为 `$codex-sdd` 的阶段操作。
- 失败/部分结果/规则缺失处理：保留并强化为不可静默降级。
