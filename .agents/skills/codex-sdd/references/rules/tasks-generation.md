# 任务生成规则

核心原则  

### 1. 自然语言描述

关注能力和结果，而非代码结构。  

描述：  

要实现的功能  
业务逻辑和行为  
特性和能力  
领域语言和概念  
数据关系和工作流  
避免：  

文件路径和目录结构  
函数/方法名和签名  
类型定义和接口  
类名和 API 契约  
具体数据结构  
理由：实现细节（文件、方法、类型）在 design.md 中定义。任务描述要完成的功能工作。  

### 2. 任务排序原则

排序隐含依赖：任务 N 隐式依赖于它之前的所有任务。这是主要的依赖机制。  

任务必须遵循以下阶段顺序：  

基础：环境设置、测试基础设施、共享工具类、数据库模式、配置  
核心：主要功能实现（可并行任务在此分组）  
集成：连接组件、跨边界连接  
验证：E2E 测试、边缘情况、回归检查  
理由：基础工作解锁其他所有内容。早期放置设置任务可防止下游阻塞。核心任务通常可以并行运行，因为基础已完成。  

### 3. 任务集成与推进

每个任务必须：  

建立在之前的输出之上（无孤立代码）  
连接到整个系统（无悬空功能）  
渐进式推进（复杂度无大跳跃）  
尊重 design.md 中定义的架构边界（架构模式与边界映射）  
遵守 design.md 中记录的接口契约  
谨慎使用主任务摘要——如果工作已完全被子任务捕获，省略详情子弹。  
以集成任务结尾将所有内容连接在一起。  

### 4. 依赖声明

默认：顺序排序处理大多数依赖（任务 N 依赖于它之前的任务）。  

需要显式声明的情况：  

任务依赖于不同主任务组中的特定任务（跨边界）  
依赖从排序本身不明显  
任务可以跳过其位置（通过 (P) 声明）但仍需要特定的先前工作  
格式：_Depends: 1.2, 2.3_——与 _Requirements:_ 一起放在任务详情章节中。  

不要过度标注：如果任务仅依赖于它直接前面的任务，排序本身就足够了。  

### 5. 边界范围

每个任务应声明其组件边界，使用 design.md 组件/模块名称：  

_Boundary: AuthService_ 或 _Boundary: API Layer, UserRepository_  
帮助验证并行安全性：边界不重叠的任务是并行候选  
帮助代理理解范围：触及什么和不触及什么  
何时使用：标记为 (P) 的任务必须声明以验证并行安全性。对于范围从描述中显而易见的顺序任务可省略。  

边界规则：  

每个可执行任务应保持在单一责任边界内  
如果工作必须跨越边界，将其作为显式集成任务，而非普通实现任务  
不要在看似局部的任务中隐藏跨边界协调  

### 6. 灵活的任务大小

指南：  

主任务：根据需要设置任意多的子任务（按内聚性分组）  
子任务：只承诺一个内聚、可独立验证的结果，通常包含 3-10 个必要详情子弹  
按依赖、责任边界和可观察完成条件在太细和太宽之间取得平衡，不使用人工工时作为粒度标准  
不要强制任意数字——让逻辑分组决定结构。  

### 7. 需求映射

在每个任务详情章节末尾：  

_Requirements: X.X, Y.Y_ 仅列出数字需求 ID（逗号分隔）。绝不追加描述性文本、括号、翻译或自由格式标签。  
对于跨领域的需求，列出每个相关的需求 ID。所有需求在 requirements.md 中必须有数字 ID。如果 ID 缺失，停止并修正 requirements.md 后再继续生成任务。  
在有帮助时引用 design.md 中的组件/接口（如 _Contracts: AuthService API）  

### 7.5 可观察的完成

每个可执行任务必须包含至少一个描述可观察完成状态的详情子弹：  

将其表述为交付物、运行时行为、持久化状态、UI 状态、端点行为、测试结果或集成结果  
避免"实现支持"、"连接事物"或"处理逻辑"等模糊子弹，除非配以具体的可观察结果  
优先使一个详情子弹清晰回答："此任务完成后什么会是真的？"  
保留在现有任务主体内，不要添加额外的簿记字段  

### 8. 仅代码关注

仅包含：  

编码任务（实现）  
测试任务（单元、集成、E2E）  
技术设置任务（基础设施、配置）  
排除：  

部署任务  
文档任务  
用户测试  
营销/商业活动  

## 任务计划审查门禁

在编写 tasks.md 之前，审阅草稿任务计划并修复本地问题，直到计划通过或发现真正的规格空白。  

## 覆盖审查

requirements.md 中的每个需求 ID 必须出现在至少一个任务中。  
design.md 中的每个设计组件、接口/契约、集成点、运行时前提和验证关注点必须由至少一个任务表示。  
如果覆盖缺失是因为任务计划不完整，修复草稿任务并重新审查。  
如果因为需求或设计模糊、矛盾或规范不足而无法干净地添加覆盖，停止并返回需求/设计阶段，而不是在 tasks.md 中掩盖空白。  

## 可执行性审查

每个子任务必须按书面可执行，并可在不跨越多个责任边界的情况下独立完成和验证。  
每个子任务必须产生可验证的交付物（行为、工件、端点、UI 状态、配置、迁移、测试或集成结果）。  
每个可执行子任务必须包含至少一个声明可观察完成条件的详情子弹。  
拆分结合多个独立可验证结果的组合任务。  
拆分跨越多个责任边界的任务，除非它们是显式集成任务。  
如果许多任务需要宽泛的 _Boundary:_ 范围或重复的跨边界协调，停止并返回设计或路线图分解，而不是强行通过任务生成推进规格。  
合并或折叠太小、仅簿记或无意义的执行单元的任务。  
将隐含的前提条件显式为前置任务。  
编辑后重新检查 _Depends:_、_Boundary:_ 和 (P) 标记，使并发声明仍与设计边界和依赖图匹配。  

## 审查循环

在编写 tasks.md 之前对草稿任务计划运行审查门禁。  
如果问题局限于任务计划本地，修复草稿并重新运行审查门禁。  
保持循环有界：在升级真正的规格空白之前，不超过 2 次审查和修复轮次。  
仅在审查门禁通过后才编写 tasks.md。  

## 可选测试覆盖任务

当设计已保证功能覆盖且快速 MVP 交付被优先时，将纯测试导向的后续工作（如基线渲染/单元测试）标记为可选，使用 - [ ]* 复选框形式。  
仅当子任务直接在详情子弹中引用 requirements.md 中的验收标准时，才应用可选标记。  
绝不将实现工作或集成关键验证标记为可选——将 * 保留给可在 MVP 之后重新审视的辅助/可延期测试覆盖。  

## 任务层级规则

最多 2 层  
第 1 层：主任务（1, 2, 3, 4...）  
第 2 层：子任务（1.1, 1.2, 2.1, 2.2...）  
不更深嵌套（无 1.1.1）  
如果主任务仅包含一个可执行项，折叠结构并将子任务提升为主任务级别（如将 1.1 替换为 1.）。  
当主任务纯粹作为容器存在时，保持复选框描述简洁，避免重复详情——将具体内容保留给子任务。  

## 顺序编号

主任务必须递增：1, 2, 3, 4, 5...  
子任务在每个主任务内重置：1.1, 1.2，然后 2.1, 2.2...  
绝不重复主任务编号  

## 并行分析（默认）

假设并行分析已启用，除非显式禁用（如 --sequential 标志）。  
(P) 表示：此任务不依赖于其紧邻的前置同级任务，可以与它们并发运行。  
当所有以下条件满足时，识别可以并发运行的任务：  
对待处理任务无数据依赖  
无共享文件或资源竞争  
不需要另一个任务的前置审查/批准  
_Boundary:_ 标注确认非重叠的组件范围  
基础阶段任务很少是 (P)——它们建立共享前提条件。  
核心阶段任务是 (P) 的主要候选，因为基础已完成。  
验证已识别的并行任务在架构模式与边界映射中定义的独立边界内运行。  
确认 design.md 中的 API/事件契约不会以导致冲突的方式重叠。  
具有跨边界依赖的 (P) 任务必须显式声明 _Depends: X.X_。  
在每个可并行任务的编号后立即附加 (P)：  
示例：- [ ] 2.1 (P) 构建邮件后台工作器  
适用于主任务和子任务（如适用）。  
如果请求顺序模式，完全省略 (P) 标记。  
将并行任务逻辑分组（尽可能在同一父级下），并在详情子弹中突出显示任何排序注意事项。  
显式调用阻止 (P) 的依赖，即使任务看起来相似。  

## 复选框格式

- [ ] 1. 基础：环境和测试基础设施搭建
- [ ] 1.1 子任务描述
  - 详情项 1
  - 详情项 2
  - 可观察完成条件
  - _Requirements: X.X_

- [ ] 2. 核心功能 A
- [ ] 2.1 (P) 子任务描述
  - 详情项...
  - 可观察完成条件
  - _Requirements: Y.Y_
  - _Boundary: AuthService_

- [ ] 2.2 (P) 子任务描述
  - 详情项...
  - 可观察完成条件
  - _Requirements: Z.Z_
  - _Boundary: UserRepository_

- [ ] 3. 集成和连接
- [ ] 3.1 子任务描述
  - 详情项...
  - 可观察完成条件
  - _Depends: 2.1, 2.2_
  - _Requirements: W.W_

## 需求覆盖

强制检查：  

requirements.md 中的所有需求必须被覆盖  
交叉引用每个需求 ID 与任务映射  
如果发现空白：返回需求或设计阶段  
不应有需求没有对应的任务  
使用 N.M 格式的数字需求 ID，其中 N 是 requirements.md 中的顶级需求编号（例如：需求 1 → 1.1, 1.2；需求 2 → 2.1, 2.2），M 是该需求组内的本地索引。  

记录任何有意推迟的需求及理由。
