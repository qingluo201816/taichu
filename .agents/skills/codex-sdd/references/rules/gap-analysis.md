# 差距分析流程

## 目标

分析已校验需求与当前代码库之间的差距，为设计提供事实、选项、约束和研究项，不在本阶段做最终架构决策。

## 一、现状调查

### 资产扫描

- 相关领域、应用、基础设施和 API 模块；
- 可复用组件、服务、Protocol、工具和插件扩展点；
- 前端页面、组件、API 与类型；
- 数据模型、MongoDB 集合、生命周期和索引；
- 测试、评测、配置、Prompt、启动与观测；
- 当前资料和历史决策状态。

### 约定提取

- 命名、分层、依赖方向；
- 插件发现与注册边界；
- 领域层技术无关约束；
- 输入验证、错误和日志模式；
- 测试位置和运行命令；
- 新实现替代旧实现时的清理范围。

### 集成接口

记录：

- 输入/输出和类型；
- API/事件/批处理；
- 数据所有权和一致性；
- 外部依赖；
- UI 与后端契约；
- 启动和配置前提。

## 二、需求可行性分析

从每个数字需求 ID 提取：

- 数据和生命周期；
- API/服务/Agent/Tool；
- UI/组件；
- 业务规则与验证；
- 错误、恢复和可观测性；
- 性能、安全、可靠性；
- 迁移和兼容。

将每项标为：

- `可复用`；
- `需扩展`；
- `需新增`；
- `需删除/替换`；
- `未知，需设计研究`；
- `受规则约束`。

## 三、实现方案

### 方案 A：扩展现有组件

适用于功能自然属于现有责任边界。

必须说明：

- 修改哪些真实模块；
- 责任是否仍单一；
- 调用方与向后兼容影响；
- 测试和清理；
- 组件膨胀风险。

### 方案 B：创建新组件/边界

适用于独立职责、生命周期、依赖或现有组件已过载。

必须说明：

- 新建理由；
- 责任和数据所有权；
- 入站/出站接口；
- 与插件发现/注册机制的关系；
- 独立测试方式；
- 导航和额外抽象成本。

### 方案 C：混合方案

适用于同时需要扩展现有入口和新增独立边界。

必须说明：

- 哪些部分扩展、哪些部分新增；
- 集成任务和顺序；
- 数据/契约迁移；
- 回滚与兼容；
- 避免双实现长期共存的清理点。

不适用的方案也要简述原因，不能为了凑数量提供虚假选项。

## 四、范围外

- 不完成深度技术选型；
- 不写正式设计；
- 不编写实现代码；
- 不修改需求；
- 不提供人工工期、工时、人员或排期。

外部依赖和未知架构点记录为设计研究项。

## 五、复杂度与风险

### 复杂度（不含时间）

- **低**：现有明确模式内的局部扩展，依赖少，无迁移。
- **中**：新增边界或少量集成，契约清晰，验证路径已知。
- **高**：跨多个边界、数据迁移、复杂状态或外部集成。
- **极高**：架构级变更、关键未知、广泛兼容或高风险数据迁移。

每个标签必须说明影响面、依赖、未知项、迁移和验证负担，不得换算成天数。

### 风险

- **高**：未知技术/契约、核心数据或安全、不可逆迁移、启动链变化。
- **中**：已知模式但集成/并发/性能需要专门验证。
- **低**：既有模式、明确范围、可回滚、验证充分。

## 六、输出

`gap-analysis.md` 必须包含：

1. 调查范围和证据。
2. 需求到资产矩阵。
3. 现有架构约束。
4. 方案 A/B/C（实际适用者）和权衡。
5. 复杂度与风险及理由。
6. 设计阶段建议。
7. 需继续研究项。
8. Graphify 覆盖或源码降级说明。
9. 旧实现清理和测试关注点。

## 原则

- 信息优先于决策；
- 多个真实可行方案；
- 假设与未知明确；
- 与当前项目事实一致；
- 复杂度透明但无工时；
- 所有结论可复现。
