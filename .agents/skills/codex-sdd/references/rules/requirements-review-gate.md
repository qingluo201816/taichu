# 需求审查门禁

在编写 requirements.md 之前，审阅草稿需求并修复本地问题，直到草稿通过或发现真正的作用域歧义。  

## 边界连续性

在各阶段之间一致地使用边界术语，但不要将需求变成设计：  

发现阶段识别 边界候选  
需求阶段在范围可能被误读时明确包含、排除和相邻期望  
设计阶段将其转化为 边界承诺  
任务阶段使用 _Boundary:_ 约束可执行工作  
需求应以用户或运营者可观察的术语澄清功能边界，而非架构所有权或实现细节。  

## 范围和覆盖审查

草稿必须覆盖功能的核心用户旅程、主要作用域边界、主要错误场景和对用户或运营者可见的有意义的边缘条件。  
如果功能涉及相邻系统、规格或工作流，草稿必须明确本功能从它们期望什么，以及它不拥有的内容（当这种区别影响用户可见行为或运营者期望时）。  
在范围内时，必须显式反映业务/领域规则、合规约束、安全/隐私期望和对用户可见行为有实质性影响的运营约束。  
如果覆盖缺失是因为草稿不完整，修复草稿并重新审查。  
如果因为项目描述或 steering 上下文模糊、矛盾或规范不足而无法完成覆盖，停止并要求用户澄清，而非猜测。  

## EARS 和可测试性审查

每个验收标准必须遵循 ears-format.md 中定义的 EARS 规则。  
每个需求必须是可测试的、可观察的，且足够具体，使后期的设计和验证可以验证它。  
移除属于 design.md 而非 requirements.md 的实现细节。  
需求标题必须仅使用数字 ID；不混合数字和字母标签。  

## 结构和质量审查

将相关行为分组为连贯的需求区域，不在多个章节中重复相同的义务。  
当功能范围可能被误读时，明确包含/排除边界。  
保持边界声明轻量且可观察：描述功能责任和相邻期望，不规定组件、层或内部所有权。  
确保非功能期望保持用户可观察或运营者可观察；将技术选择和内部架构细节移出需求。  
当源材料支持时，将"快速"、"稳健"或"安全"等模糊语言规范化为具体的用户可见期望。  

## 机械检查

在应用判断之前，先进行机械验证：  

存在数字 ID：每个需求标题都有数字 ID（1, 1.1, 2 等）。扫描草稿中没有 ID 的标题。  
存在验收标准：每个需求至少有一个 EARS 格式的验收标准。扫描没有 "When/If/While/Where/The system shall" 结构的需求。  
无实现语言：扫描属于设计而非需求的技术特定术语（数据库名称、框架名称、API 模式）。标记任何发现的项。  

## 审查循环

先运行机械检查，然后进行基于判断的审查。  
如果问题局限于草稿，修复草稿并重新运行审查门禁。  
保持循环有界：在将真正的歧义升级给用户之前，不超过 2 次审查和修复轮次。  
仅在审查门禁通过后才编写 requirements.md。
