# 错误处理标准

> 使用边界：本文件只提供项目事实审计的结构提纲，不代表太初已采用其中的通用示例。只有现有项目规则、真实代码/测试/配置或用户明确决策支持的内容，才可增量写入对应权威资料；不得创建平行项目记忆文件。
[目的：统一错误的分类、格式、传播、日志记录和监控方式]  

## 哲学

尽可能快速失败；在系统边界优雅降级  
全栈一致的错误格式（人类和机器可读）  
已知错误在源头附近处理；未知错误上报全局处理器  

## 分类（按来源决定处理）

客户端：输入/验证/用户操作问题 → 4xx  
服务端：系统故障/意外异常 → 5xx  
业务：规则/状态违规 → 4xx（如 409）  
外部：第三方/网络故障 → 映射到 5xx 或 4xx（带上下文）  

## 错误格式（单一规范格式）

{  
  "error": {  
    "code": "ERROR_CODE",  
    "message": "人类可读消息",  
    "requestId": "trace-id",  
    "timestamp": "ISO-8601"  
  }  
}  
原则：稳定的 code 枚举、无密钥、包含跟踪信息。  

## 传播（在哪里转换）

API 层：将领域错误转换为 HTTP 状态码 + 规范体  
服务层：抛出类型化的业务错误，避免字符串类型错误  
数据/外部层：将提供商错误包装为安全、可操作的代码  
未知错误：冒泡到全局处理器 → 500 + 通用消息  

### 示例模式：

try { return await useCase(); }  
catch (e) {  
  if (e instanceof BusinessError) return respondMapped(e);  
  logError(e); return respondInternal();  
}  

## 日志记录（上下文优于噪音）

记录：操作、userId（如可用）、code、message、堆栈、requestId、最小上下文。不记录：密码、令牌、密钥、完整 PII、包含敏感数据的完整请求体。  
级别：ERROR（故障）、WARN（可恢复/边界）、INFO（关键事件）、DEBUG（诊断）。  

## 重试（仅在安全时）

重试条件：网络/超时/瞬时 5xx 且操作是幂等的。 不重试：4xx、业务错误、非幂等流程。 策略：指数退避 + 抖动、限制尝试次数；需要幂等键。  

## 监控与健康

跟踪：按 code/类别的错误率、延迟、饱和度；在峰值/SLI breaches 时告警。 暴露健康：/health（存活）、/health/ready（就绪）。将错误关联到追踪。  

关注模式和决策，无实现细节或穷举列表
