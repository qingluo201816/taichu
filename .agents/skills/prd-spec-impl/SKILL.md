# PRD Spec Implementation

## 定位

为已完成设计的规格生成实现任务，等待用户确认后执行代码实现和验证。

## 输入

- 规格名称：`{版本号}/{功能名}`。
- 支持通配符，例如 `V1.0/*`。

## 输入校验

1. 规格名称非空。
2. `.kiro/specs/` 下存在匹配目录。
3. 每个目录包含 `spec.json` 和非空 `design.md`。
4. `spec.json` 的 `stage` 为 `design`、`tasks`、`implementing` 或 `completed`。
5. 匹配多个目录时，展示清单并等待用户确认。

## 流程

### Step 1 定位规格目录

读取每个匹配规格的 `spec.json`、`requirements.md`、`design.md`，确认阶段和审批状态。

### Step 2 生成任务清单

参照 `.claude/rules/KIRO_COMMAND_CALLING_SPEC.md` 的 `spec-tasks` 模板生成 `tasks.md`。

任务清单必须满足：

- 标题为 `# 实现计划`。
- 使用 `- [ ]` 复选框。
- 每个任务标注需求来源和边界范围。
- 包含测试或验证任务。
- 若涉及前端，包含视觉、响应式和交互验收。

格式不合规时，询问用户重试、跳过或终止。

### Step 3 用户确认任务

展示任务摘要并等待用户选择：

- 确认执行实现。
- 查看任务详情。
- 终止流程。

用户未确认前不得改代码。

### Step 4 TDD 实现

参照 `.claude/rules/KIRO_COMMAND_CALLING_SPEC.md` 的 `spec-impl` 模板执行：

1. RED：补失败测试或明确可复现验收。
2. GREEN：实现最小可用改动。
3. REFACTOR：只做必要整理，不扩大范围。
4. VERIFY：运行相关验证命令。

遵守太初规则：

- 使用 `uv`。
- 不回滚用户已有改动。
- 不引入无关依赖。
- 不破坏 `start.bat`。

### Step 5 验证门禁

必须执行三阶验证：

| 门禁 | 内容 |
|---|---|
| 需求与任务验收 | 需求覆盖、任务完成、无遗漏 |
| 设计验收 | 实现与 `design.md` 一致 |
| 整体验证 | 测试、静态检查、启动或页面验证按影响范围执行 |

任一门禁失败，先修复并重新验证；仍失败时停止并报告。

### Step 6 更新规格状态

验证通过后更新 `spec.json`：

- `stage` 为 `completed`。
- `approvals.implementation.completed` 为 `true`。
- 记录验证命令和结果摘要。

### Step 7 实现报告

输出中文报告：

| 字段 | 内容 |
|---|---|
| 规格名称 | {规格名称} |
| 执行任务 | {任务数量} |
| 新增文件 | {文件列表} |
| 修改文件 | {文件列表} |
| 验证结果 | {命令与结果} |
| 状态 | 完成、部分完成或失败 |

## 异常处理

| 场景 | 处理 |
|---|---|
| 规格不存在 | 提示先执行 `prd-design-generator` |
| `design.md` 缺失 | 提示先完成设计阶段 |
| 任务清单不合规 | 询问重试、跳过或终止 |
| 测试失败 | 修复后重跑；仍失败则停止报告 |
| 验证门禁未通过 | 不更新为完成状态 |
