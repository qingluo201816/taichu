现有资产探查规则
适用范围：所有规格在 spec-requirements 和 spec-design 阶段执行前 目标：避免重复建设、识别影响面、确保新代码不破坏已有功能

零、强制原则
在执行任何需求编写或设计工作之前，必须先完成本规则定义的三步探查。

❌ 禁止跳过探查直接编写 requirements.md 或 design.md
❌ 禁止基于假设推断现有系统行为（"我认为已有 XX 功能"）
✅ 必须基于实际文档或代码给出探查结论
✅ 探查结论必须记录到 requirements.md 的"现有资产探查"章节
一、功能介绍文档查阅（宏观 → 业务层）
触发条件
需求涉及已有业务功能（账单、计费、对账、配置等）的修改、增强或关联。

执行步骤
在项目的功能文档目录下搜索相关文档（如 docs/workflows/、docs/features/）
搜索关键词：需求中的业务名词、操作名称（如"批量操作"、"对账"、"付款申请"）
阅读匹配文档的"一、功能概述"和"三、核心流程"章节
确认需求与现有功能的关系：
增强：需求是现有功能的扩展（新增字段、新增操作类型）
新增：需求描述的业务场景在现有文档中无对应描述
无关联：需求属于独立功能，不影响现有功能
探查目标（必须逐项确认）
 需求功能是否已有文档描述？
 现有业务流程是否兼容？（新需求是否会与现有流程冲突）
 涉及哪些数据库表和接口？
 是否有性能优化/异常处理需要继承？
结果记录
探查结果必须写入 requirements.md → "功能介绍文档查阅（先）"章节，包含：

匹配到的文档路径
文档中描述的核心类/方法
新需求与现有功能的差异点
如果无匹配文档，标注"无现成功能介绍文档"，并说明后续将通过代码确认
二、代码图谱探查（微观 → 代码层）
注意：如项目配置了知识图谱工具（如 Graphify），优先使用图谱探查；否则使用 Grep/Glob 手动分析。

触发条件
基于功能文档探查结果，需要进一步确认代码级影响面。

执行步骤
如项目有知识图谱工具，使用图谱查询调用链（参考项目图谱文档）
如无图谱工具，使用 Grep 搜索核心类/方法名，手动分析调用关系：
# 查找谁调用了某方法
grep -rn "methodName" src/ --include="*.java"

# 查找某类的所有引用
grep -rn "ClassName" src/ --include="*.java"
对功能文档中提到的核心类/方法，逐一执行调用链查询，确认：
该类的现有调用方（修改是否影响上游）
该类的下游依赖（新增功能是否可复用）
探查目标（必须逐项确认）
 文档中提到的核心类是否已存在？代码结构与文档是否一致？
 已有方法的调用方有哪些？（修改影响分析）
 是否跨模块调用？（依赖方向是否合规，参考 HARNESS.md 跨包规则）
 God Node 是否涉及变更？（高复杂度类需额外谨慎，优先新建独立类而非修改 God Class）
结果记录
探查结果必须写入 requirements.md → "代码图谱探查（后）"章节，使用表格格式：

探查项	发现	对需求的影响
已有相关类	...	...
调用方影响	...	...
跨模块依赖	...	...
功能文档匹配	...	...
三、代码验证（兜底确认）
触发条件
功能文档或知识图谱探查后，仍有不确定之处。

执行步骤
使用 Grep 搜索需求中的关键类名/方法名，确认代码实际存在
读取核心方法的签名和实现，确认：
方法参数是否与需求匹配
方法返回值是否满足需求
是否有隐藏的副作用
检查相关的 DTO/Entity/Enum 是否已存在，是否需要新增字段
结果记录
验证结论补充到 requirements.md 的探查结果表格中，标注"代码验证"行。

探查顺序总结
一、功能介绍文档查阅（业务宏观）
        ↓ 有匹配文档？
    YES │ → 确认业务流程兼容性
    NO  │ → 标记"无现成文档"，进入第二步
        ↓
二、代码图谱探查（代码微观）
        ↓ 有不确定之处？
    YES │ → 进入第三步
    NO  │ → 探查完成
        ↓
三、代码验证（兜底确认）

四、前端资产发现规则
当规格涉及用户界面变更时，除查询后端 Controller/Service 外，还需查询前端资产。

触发条件
规格描述中包含以下任一情况：

新增页面、新增弹窗、新增表单
修改现有页面布局/表格列/操作按钮
新增前端交互流程（如审批流、状态流转）
执行步骤
匹配前端业务域：根据规格业务关键词，在前端代码中搜索相关页面和组件
匹配前后端 API：查找前端 API 调用文件，确认涉及的前后端接口
查询页面调用关系：分析页面组件的调用关系，获取受影响的配置文件
查询命令示例：

# 搜索前端页面
grep -rn "关键词" src/views/ --include="*.tsx" --include="*.vue"

# 搜索 API 函数
grep -rn "apiName" src/api/ --include="*.ts"

# 搜索组件引用
grep -rn "ComponentName" src/ --include="*.tsx" --include="*.vue"
探查目标（必须逐项确认）
 规格涉及的页面是否已存在？页面路径是什么？
 现有页面是否有匹配的 API 函数？需要新增还是修改？
 config.ts 中是否有对应的表格列/表单配置需要变更？
 是否涉及弹窗（modal）的新增或修改？
结果记录
探查结果写入 requirements.md → "前端资产探查"章节，使用表格格式：

探查项	发现	对需求的影响
已有相关页面	...	...
已有 API 函数	...	...
config.ts 配置	...	...
弹窗组件	...	...
无匹配前端资产	标注"无现成前端资产"	需新增页面/API/组件
探查顺序总结
后端资产探查（已有：功能文档 → 代码图谱 → 代码验证）
        ↓ 规格涉及 UI 变更？
    YES │ → 进入前端资产探查
    NO  │ → 探查完成
        ↓
前端资产探查：业务关键词搜索 → API 调用分析 → 页面调用链 → 代码验证
