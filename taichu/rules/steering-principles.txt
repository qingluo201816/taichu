Steering 原则
Steering 文件是项目记忆，而非详尽的规范。

内容粒度
黄金法则
"如果新代码遵循现有模式，steering 就不需要更新。"

✅ 应记录
组织模式（功能优先、分层）
命名约定（PascalCase 规则）
导入策略（绝对路径 vs 相对路径）
架构决策（状态管理）
技术标准（关键框架）
❌ 应避免
完整文件列表
每个组件的描述
所有依赖关系
实现细节
代理特定工具目录（如 .cursor/、.gemini/、.claude/）
.kiro/ 元数据目录（settings、自动化）的详细文档
示例对比
不好（类似规范）：

- /components/Button.tsx - 带变体的主按钮
- /components/Input.tsx - 带验证的文本输入
- /components/Modal.tsx - 模态对话框
...（50+ 文件）
好（项目记忆）：

## UI 组件（`/components/ui/`）
可复用的、与设计系统对齐的原语
- 按功能命名（Button、Input、Modal）
- 导出组件 + TypeScript 接口
- 无业务逻辑
安全
绝不包含：

API 密钥、密码、凭证
数据库 URL、内部 IP
机密或敏感数据
质量标准
单一领域：每个文件一个主题
具体示例：用代码展示模式
说明理由：为什么做出这些决策
可维护的大小：通常 100-200 行
保留（更新时）
保留用户章节和自定义示例
默认追加（添加，不替换）
添加 updated_at 时间戳
注明变更原因
注意事项
模板是起点，按需定制
遵循与核心 steering 相同的粒度原则
所有 steering 文件作为项目记忆加载
对 .kiro/specs/ 和 .kiro/steering/ 的轻量引用是可接受的；避免其他 .kiro/ 目录
自定义文件与核心文件同等重要
文件特定焦点
product.md：目的、价值、业务上下文（非详尽功能）
tech.md：关键框架、标准、约定（非所有依赖）
structure.md：组织模式、命名规则（非目录树）
自定义文件：专用模式（API、测试、安全等）9ol
