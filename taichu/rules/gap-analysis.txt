差距分析流程

目标
分析需求与现有代码库之间的差距，为实现策略决策提供依据。

分析框架
1. 现状调查
扫描领域相关资产：

关键文件/模块和目录布局
可复用组件/服务/工具
主要架构模式和约束
提取约定：

命名、分层、依赖方向
导入/导出模式和依赖热点
测试位置和方法
记录集成接口：

数据模型/模式、API 客户端、认证机制
2. 需求可行性分析
从 EARS 需求中列出技术需求：

数据模型、API/服务、UI/组件
业务规则/验证
非功能性需求：安全性、性能、可扩展性、可靠性
识别差距和约束：

当前代码库中缺失的能力
待后续研究的未知项（标记为"需研究"）
现有架构和模式带来的约束
记录复杂性信号：

简单 CRUD / 算法逻辑 / 工作流 / 外部集成
3. 实现方案选项
方案 A：扩展现有组件
适用场景：功能自然融入现有结构

需扩展的文件/模块：

识别需要修改的具体文件
评估对现有功能的影响
评估向后兼容性问题
兼容性评估：

检查扩展是否遵循现有接口
验证不会对调用方造成破坏性变更
评估测试覆盖率影响
复杂性和可维护性：

评估新增功能的认知负担
检查是否遵循单一职责原则
评估文件大小是否保持可控
权衡：

✅ 最少新文件，初始开发更快
✅ 利用现有模式和基础设施
❌ 存在现有组件膨胀的风险
❌ 可能使现有逻辑复杂化
方案 B：创建新组件
适用场景：功能具有独立职责或现有组件已较为复杂

新建的理由：

清晰的关注点分离证明新文件合理
现有组件已经复杂
功能具有独立的生命周期或依赖
集成点：

新组件如何连接到现有系统
暴露的 API 或接口
对现有组件的依赖
职责边界：

明确定义新组件的职责范围
与现有组件的接口
数据流和控制流
权衡：

✅ 清晰的关注点分离
✅ 更易于独立测试
✅ 降低现有组件的复杂性
❌ 需要导航更多文件
❌ 需要仔细的接口设计
方案 C：混合方案
适用场景：复杂功能需要同时扩展和新建

组合策略：

哪些部分扩展现有组件
哪些部分需要新建组件
它们如何交互
分阶段实现：

初始阶段：最小可行变更
后续阶段：重构或新组件
必要时制定迁移策略
风险缓解：

渐进式发布方法
功能开关或配置
回滚策略
权衡：

✅ 适用于复杂功能的平衡方案
✅ 允许迭代优化
❌ 需要更复杂的规划
❌ 协调不当可能导致不一致
4. 差距分析范围之外
将深度研究活动推迟到设计阶段。
仅将未知项记录为简洁的"需研究"条目。
5. 实现复杂度与风险
工作量：
S（1-3 天）：现有模式，最少依赖，直接集成
M（3-7 天）：一些新模式/集成，中等复杂度
L（1-2 周）：重要功能，多个集成或工作流
XL（2+ 周）：架构变更，不熟悉的技术，广泛影响
风险：
高：未知技术，复杂集成，架构变更，不明确的性能/安全路径
中：有指导的新模式，可管理的集成，已知的性能解决方案
低：扩展既有模式，熟悉的技术，明确的范围，最少的集成
输出清单
需求到资产映射，标注差距（缺失 / 未知 / 约束）
方案 A/B/C 及简要理由和权衡
工作量（S/M/L/XL）和风险（高/中/低）各附一行理由
设计阶段建议：
优选方案和关键决策
待后续研究的条目
原则
信息优先于决策：提供分析和选项，而非最终选择
多个可行选项：在适用时提供可信的备选方案
明确差距和假设：清晰标注未知项和约束
基于上下文：与现有模式和架构限制保持一致
透明的工作量和风险：简明扼要地论证标签
