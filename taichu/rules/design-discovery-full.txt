设计发现流程（完整版）
目标
进行全面研究和分析，确保技术设计基于完整、准确和最新的信息。

发现步骤
1. 需求分析
将需求映射到技术需求

从 EARS 格式中提取所有功能需求
识别非功能需求（性能、安全、可扩展性）
确定技术约束和依赖关系
列出核心技术挑战
2. 现有实现分析
理解当前系统（如果是修改/扩展现有系统）：

分析代码库结构和架构模式
映射可复用的组件、服务、工具类
识别领域边界和数据流
记录集成点和依赖关系
确定策略：扩展 vs 重构 vs 包装
2.5 前端架构深度分析
引用前端探索规则：读取并执行 .kiro/settings/rules/frontend-exploration-rules.md 中定义的全部探索步骤。

执行要求：

按照 frontend-exploration-rules.md 第三章"探索步骤"中的 7 个步骤依次执行
使用第二章"图谱查询命令"中的命令进行高效查询
按照第四章"输出要求"将发现记录到 research.md 的"前端架构分析"章节
如图谱不可用，按照第五章"降级策略"执行
3. 技术研究
调查最佳实践和解决方案：

使用 WebSearch 查找：

类似问题的最新架构模式
技术栈的行业最佳实践
相关技术的最近更新或变更
常见陷阱和解决方案
使用 WebFetch 分析：

框架/库的官方文档
API 参考和使用示例
迁移指南和破坏性变更
性能基准测试和对比
4. 外部依赖调查
针对每个外部服务/库：

搜索官方文档和 GitHub 仓库
验证 API 签名和认证方式
检查与现有技术栈的版本兼容性
调查速率限制和使用约束
查找社区资源和已知问题
记录安全注意事项
标注需要在实现阶段进一步调查的空白点
5. 架构模式与边界分析
评估架构方案：

对比相关模式（MVC、Clean、Hexagonal、Event-driven）
评估与现有架构和 steering 原则的契合度
识别需要避免团队冲突的领域边界和所有权分界
考虑可扩展性影响和运维关注点
评估可维护性和团队技术栈熟悉度
在 research.md 中记录首选模式和被拒绝的替代方案
6. 风险评估
识别技术风险：

性能瓶颈和扩展限制
安全漏洞和攻击向量
集成复杂度和耦合程度
技术债务的创建 vs 解决
知识缺口和培训需求
研究指南
何时搜索
始终搜索：

外部 API 文档和更新
认证/授权的安全最佳实践
已识别瓶颈的性能优化技术
依赖的最新版本和迁移路径
不确定时搜索：

特定用例的架构模式
数据格式/协议的行业标准
合规要求（GDPR、HIPAA 等）
预期负载的扩展方案
搜索策略
从官方来源开始（文档、GitHub）
查看最近的博客文章和文章（过去 6 个月）
查阅 Stack Overflow 上的常见问题
调查类似的开源实现
输出要求
将所有影响设计决策的发现记录到 research.md 中，使用共享模板：

影响架构、技术对齐和契约的关键洞察
研究期间发现的约束
推荐的方法和选定的架构模式及理由
被拒绝的替代方案和权衡（记录在设计决策章节）
更新领域边界，用于指导组件和接口契约
风险和缓解策略
需要在实现期间进一步调查的空白点
